## 2026-09-05 — 맥·윈도우 배포판 (Phase 6)

터미널 없이 **설치해서 쓰는 앱**이 됐다. 만드는 방법과 함정은
[PACKAGING](PACKAGING.md) 에 있다.

- `npm run dist:mac` → `.dmg` 두 개 (Apple Silicon · Intel). **실제로 만들어
  실행까지 확인했다** — 앱이 서버를 띄우고 조작·출력·프로젝터·강사 화면이 다 뜬다.
- 윈도우 설치 파일은 **GitHub Actions** 가 만든다 (개발용 맥에 Wine 이 없다).
  저장소 Actions 탭 → '설치 파일 빌드'.
- 자료는 배포판에 **들어가지 않는다.** 가사·성경·악보는 저작권 자료라 git 에도
  설치 파일에도 없다. 설정 탭의 자료 내보내기/가져오기로 각 PC 에 넣는다.

**데이터 저장 위치** — 맥 `~/Library/Application Support/sermon-presentation/data/`,
윈도우 `%APPDATA%\sermon-presentation\data\`. 앱 안에는 쓸 수 없다(맥 `.app` 은
읽기 전용, 윈도우 `Program Files` 는 관리자 권한). `data` 한 칸 아래에 두는 이유는
그 위에 Electron 이 자기 캐시를 만들기 때문이다 — 섞이면 '이 폴더만 복사하면
이사가 됩니다' 가 거짓이 된다.

**개발 방식은 그대로다.** 지금처럼 `.ts` 를 그대로 실행한다. 포장할 때만
`tsc` 로 JS 를 뽑는다 — Electron 의 Node 가 타입 스트리핑을 해 준다는 보장이 없다.

가장 오래 걸린 함정: **앱 이름을 한글로 두니 창도 로그도 없이 죽었다.**
`productName` 은 Helper 앱 이름이 되는데 Electron 이 한글 이름의 Helper 를 찾지
못한다. 이름은 영문으로 두고 보이는 이름만 한글로 했다.

## 2026-09-05 — 자료를 옮겨도 예배 순서의 곡이 그대로 열린다

'집에서 준비하고 교회에서 실행하려면' 을 확인하다 두 가지가 드러났다.

**① 옮기면 순서의 곡 연결이 끊겼다.** 예배 순서 항목은 곡을 `songId` 로 가리키는데,
가져오기가 곡을 새로 만들면 id 가 새로 매겨진다. 그 항목의 `songId` 는 그대로라
**순서에 제목은 보이는데 누르면 '곡을 찾을 수 없습니다'** 가 됐다 — 예배 중에
만나는 오류다. 실제 DB 는 곡을 지운 자리마다 id 에 구멍이 있어 거의 확실히 어긋났다.

→ 가져오기가 **'번들의 옛 id → 이 PC 의 새 id' 표**를 들고 순서 항목을 이어 준다.
양쪽이 같은 번들 안에 있으므로 짐작할 것이 없다. 이을 곳이 없는 항목은
**조용히 넘기지 않고** 결과에 적는다 — 예배 전에 알아야 고칠 수 있다.

**② 합치기가 곡을 복제했다.** 같은 번들을 두 번 넣으면 곡이 통째로 두 배가 됐다.

→ 이미 있는 곡은 건너뛰고 **그 곡으로 이어 준다.** 짝을 맞추는 기준은
`(곡집, 번호) + 제목` 이다. 번호만으로는 안 된다 — 같은 번호를 두 곡이 갖는
경우가 실제로 35건 있어서, 번호만 보면 그중 한 곡이 조용히 사라진다.
번호가 없는 곡('기타' 등)은 제목으로 알아본다.

실측(격리 서버 두 대, 집 → 교회):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 순서가 가리키는 곡 | `songId 3` → **없음** | `songId 1` → **셋째곡** |
| 같은 번들을 세 번 합치면 | 곡 2 → 4 → 6 | 곡 **2 그대로** |

검증: `tsc` · `vitest` 1,290개(신규 19) · `vite build`.

## 2026-09-04 — 종료할 때 곡 DB 를 닫는다

'데이터 폴더를 드랍박스에 두면 되지 않느냐' 는 질문을 확인하다 찾았다.

종료 처리가 성경 DB 와 앱 DB 만 닫고 **곡 DB 를 닫지 않았다.** 닫아야 SQLite 가
WAL 을 본체에 합치고 `-wal`·`-shm` 을 지운다.

실측 — 정상 종료(`Ctrl+C`) 뒤인데도:

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| `songs.sqlite` | 4KB | **98KB** |
| `songs.sqlite-wal` | 234KB | 없음 |
| 그 한 파일만 복사해 열면 | `no such table: songs` | 곡이 그대로 보인다 |

평소 쓰는 데는 탈이 없었다 — 다음에 열 때 SQLite 가 WAL 을 읽는다. 문제는
**파일을 복사하거나 클라우드로 동기화할 때**다. 빈 DB 가 그대로 따라간다.
`snapshotDatabases()`(`VACUUM INTO`)를 쓰라는 규칙이 있는 이유가 이것인데,
종료 뒤에도 같은 함정이 남아 있었다.

## 2026-09-04 — 악보는 **켤 때만** 나간다 · 조작 화면에서 켜고 끈다

사용자 보고 셋을 한 번에 고쳤다.

**① 기본이 가사가 됐다.** 단 경계 자동 검출이 아직 불완전하다 — 틀린 자리가 벽에
걸리는 것보다 가사가 낫다. **가사는 늘 맞다.** 이제 악보는 항목마다 켜야 나간다.

**② 조작 화면에서 켠다.** 찬양 탭 곡 카드와 예배 순서의 찬양 항목 설정에
**`가사 | 악보`** 가 생겼다. 악보가 없는 곡이면 단추가 흐려지고 '악보 없음' 이라고
말해 준다 — 눌러도 아무 일이 없으면 고장으로 보인다.

**③ 프로젝터의 `S` 가 보이는 단추가 됐다.** 이게 내 잘못이었다. `S` 는 키보드에만
있었고 막대에도 안내문에도 없어서, 한 번 끈 사용자가 **되돌리는 법을 찾을 수
없었다.** 게다가 `localStorage` 에 남아 다음 주에도 꺼진 채였다.

- 막대에 **`가사`/`악보` 단추**를 넣었다. 글자는 **지금 나가고 있는 것**이다.
- **저장하지 않는다.** 창을 다시 열면 조작 화면의 설정을 따른다 — 주인은 조작 화면이다.
- 안내문에 `S 가사↔악보` 를 적었다.
- 이 창의 단추는 이제 **급할 때의 탈출구**다. 악보가 이상하게 잘려 나가면 여기서
  즉시 가사로 바꾸고, 다시 눌러 돌아온다.

OBS 출력과 강사 모니터는 **언제나 가사**입니다 — 이건 그대로입니다.

구조: 프로젝터는 `deck` 을 받지 않고 `state.slide` 한 장만 본다. 그래서 '악보로
낸다' 는 결정이 **슬라이드에 실려야** 하고, 서버가 `?sheet=1` 일 때만 싣는다.

검증: `tsc` · `vitest` 1,271개 · `vite build`. 격리 서버에서 조작 화면과 프로젝터
창을 함께 띄우고 양방향으로 확인했다.

## 2026-09-04 — 악보 단 경계를 사람이 확인한다 (D-6 ⑥ · D-6 완료)

오선을 다섯 줄 찾지 못한 악보가 **155장**(2,061장의 7.5%) 있는데, 사람이 볼 자리가
없었다. **검토 탭**에 `가사 줄나눔 | 악보 단 경계` 전환을 두고 그 자리를 만들었다.

**그림 위에 잘리는 자리를 겹쳐 그린다** — 이게 이 화면의 전부다. '6번째 단이 4줄'
같은 숫자만으로는 맞는지 알 수 없고, 잘린 자리를 눈으로 봐야 한 번에 판단된다.
줄 수가 5가 아닌 단은 **빨간 점선**으로 따로 칠한다.

- `Enter` 괜찮음 + 다음 · `↑↓` 이동 — 가사 검토와 **같은 손버릇**이다.
- 잘못 눌렀으면 **판정 취소**. 155장을 훑다 한 번 잘못 누르면 그 장을 다시 만날
  방법이 없어지므로 물릴 길을 반드시 둔다.
- 판정한 장도 목록에 남되 **뒤로 간다** — 빼 버리면 방금 누른 것이 눈앞에서 사라진다.
- **악보를 다시 검출해도 판정은 남는다** (`putSheet` 가 아예 받지 않는다).

**이 표시는 '틀렸다' 가 아니라 '봐야 한다' 는 뜻이다.** 실제로 5번(6단 중 6번째가
4줄)을 화면에서 보니 빨간 칸이 마지막 오선과 가사 두 줄을 정확히 감싸고 있었다 —
사람이 할 일은 '괜찮음' 한 번이다. 그래서 이 화면은 고치는 것보다 **빠르게 넘기는
것**에 맞춰 만들었다.

만들면서 잡은 것: **판정을 눌러도 진행 막대가 0 에 머물렀다.** 목록 줄만 고치고
숫자를 그대로 뒀기 때문인데, 155장을 훑는 내내 일이 쌓이는 것이 안 보이면 손이 지친다.

검증: `tsc` · `vitest` 1,269개(신규 19) · `vite build`. 격리 서버에서 실제 155장으로
확인했다 — 사용자 DB 는 `VACUUM INTO` 사본을 뜨고 악보 폴더는 읽기만 했다.

**남은 판단**: 경계를 끌어서 고치는 길은 아직 없다. 먼저 155장을 훑어 **정말 틀린
것이 몇 장인지** 세어 본 뒤에 정하는 것이 맞다.

## 2026-09-04 — 열 너비를 마우스로 끌어 정한다

세로 열 비율이 CSS 에 박혀 있었다. 쓰는 화면이 사람마다 달라 — 방송실의 넓은
모니터에서는 미리보기를 키우고 싶고, 랩탑에서는 목록이 넓어야 한다.

세 곳의 경계를 끌 수 있다.

| 어디 | 무엇 ↔ 무엇 |
|---|---|
| 모든 탭 | 본문 ↔ 오른쪽 열(미리보기·송출 제어) |
| 찬양 | 곡 목록 ↔ 표시 설정 |
| 검토 | 검토 목록 ↔ 가사 |

- **되돌리는 길을 둘 둔다** — 경계를 **더블클릭**하거나, 눌러서 **Home**. 마우스로만
  조절하게 두면 잘못 끌었을 때 '원래 얼마였더라' 를 찾을 방법이 없다.
- 키보드 **←→** 로도 16px 씩 움직인다. 태블릿에서는 손가락으로 끈다.
- **끝까지 끌어도 한쪽이 사라지지 않는다.** 열이 0이 되면 그 안의 단추를 누를 수
  없게 되고, 예배 중에 그렇게 되면 되돌릴 방법을 찾느라 진행이 멈춘다.
- 이 PC 에만 남는다 (`localStorage`) — 테마와 같은 이유로 서버 설정이 아니다.
- 화면이 좁으면(900px 미만) 지금처럼 위아래로 쌓이고 경계는 숨는다.

**만들면서 잡은 것 셋** — 셋 다 코드가 아니라 화면에서 눌러 보고 알았다.

1. **CSS 변수가 자식에게 흘러갔다.** 이름이 하나뿐이라, 껍데기가 정한 오른쪽 열
   너비가 탭 **안쪽** 격자까지 내려가 아무도 끌지 않은 열이 넓어졌다.
2. `.body` 는 줄 안쪽 칸에도 쓰이는 이름이다(`.cue-row .body` 등). 지금은
   `display: flex` 가 덮어 무사하지만, 변수가 흘러가므로 `.app > .body` 로 못 박았다.
3. **화살표를 연달아 눌러도 한 칸만 움직였다.** 처리기가 아직 그려지지 않은 옛 폭을
   읽어서다. 정한 값을 곧바로 적는 곳을 따로 두어 고쳤다.

실측(격리 서버 7811, 창 1440): 왼쪽 끝 240px · 오른쪽 끝 544px(이웃 320 남김) ·
Home 으로 기본값 복귀. 검증: `tsc` · `vitest` 1,250개(신규 9) · `vite build`.

## 2026-09-04 — 악보 모양을 사람이 고친다 (D-6 ⑦)

악보의 절이 **겹쳐 적혔는지 이어 적혔는지**를 자동으로 짐작하는데, 2,061곡 중
**536곡(26%)** 이 짐작과 어긋난다. 지금까지는 그것을 고칠 길이 없었다.

찬양 탭 곡 카드의 '악보' 줄에 **자동 | 겹쳐 | 이어** 를 두었다.

- **'자동' 이 기본이고 되돌리는 길이다.** 짐작이 74%는 맞고, 나중에 자료나 규칙이
  나아지면 자동이 따라간다. 검출할 때마다 짐작한 값을 적어 두면 사람이 고친 것과
  구별할 수 없어져 규칙을 고쳐도 옛 값이 남는다 — `lines_source` 에서 겪은 함정이다.
- **악보를 다시 검출해도 고른 값은 남는다.** `putSheet` 가 `layout` 을 아예 받지
  않도록 타입으로 막았다.
- **모양이 짐작인지 사람이 고른 것인지 화면이 구별해 보여 준다** ('(짐작)' 표시).
- **송출을 다시 하지 않는다.** 지금 화면에 뜬 덱을 다시 보내면 첫 슬라이드로 튄다 —
  3절을 부르다 1절로 돌아가는 것보다 '다음 송출부터 반영됩니다' 가 안전하다.

실측(격리 서버 7810, 2절×3줄 · 단 6개): 이어 = `♪1 2 3 4 5 6` · 겹쳐 = `♪1 3 5 1 3 5`.
검증: `tsc` · `vitest` 1,241개(신규 17) · `vite build`.

**함께 알게 된 것** — 한 슬라이드에 여러 줄이 들어가면(2줄씩·섹션 전체) 그 섹션의
**첫 단만** 나간다. 슬라이드가 걸친 단 범위를 통째로 잘라야 맞다. 1줄씩 송출할 때는
정확하므로 급하지 않아 보드에 남겼다.

## 2026-09-04 — 부채 정리: 아무도 안 쓰는 길을 지웠다 (§4.6 C·E)

전수 조사에서 '자리만 잡아 둔 것' 으로 분류했던 것들을 정리했다.

### 지운 것

| 무엇 | 왜 |
|---|---|
| `t: 'show'` + `state.show()` | 단일 슬라이드 송출. 아무도 보내지 않았고 **덱을 버리는 동작**이라, 남겨 두면 LAN 의 어떤 클라이언트든 예배 중 진행 위치를 날릴 수 있었다 |
| `t: 'state:patch'` + `stage.js` 처리기 | 타입과 처리기만 있고 **서버가 한 번도 보내지 않았다** |
| `lib/song-slides.ts` `buildSongSlides` | `buildSongDeck` 과 `order` 계산이 그대로 겹쳤다 |

### 지우면서 옮긴 것 — 이게 이 작업의 핵심이다

**블랙 유지 규칙이 `show` 의 주석에만 있었다.** 2026-08-15 실사용에서 '블랙을 켜 뒀는데
다른 슬라이드를 누르니 화면이 나가 버린다' 로 드러난 것이고, `loadDeck`·`goto` 두 곳이
`(show 주석 참고)` 로 그 주석을 가리키고 있었다. 그냥 지우면 **왜 그렇게 했는지가
사라진다.** `server/state.ts` 의 '조작' 절 머리말로 옮기고, 두 주석도 그리로 가리켰다.

**테스트가 `state.show()` 를 11곳에서 썼다.** '묶음 없는 한 장' 상태를 만드는 도구로

## 2026-09-03 — 곡 수록 정보(곡집·번호) 편집 (U-4)

`PUT /api/songs/:id/entries` 와 `api.setSongEntries()` 래퍼는 있었는데 부르는 곳이
없었다. 라우트 주석에 적힌 용도 — "'이 곡은 많은물소리 42번' 을 나중에 붙일 때" —
를 하려면 DB 를 직접 만져야 했다.

찬양 탭 곡 카드에 **수록** 줄이 생겼다. `고치기` 를 누르면 편집 블록이 열린다.

```
수록  많은물소리 42   기타      [고치기]
      ┌───────────────────────────────┐
      │ 많은물소리        [42]     ✕ │
      │ 기타          번호 없음    ✕ │
      │ [＋ 곡집 추가…            ▾] │
      │ [수록 정보 저장] [취소]       │
      └───────────────────────────────┘
```

### 판단한 것

- **즉시 반영이 아니라 [저장] 을 받는다.** `setEntries` 가 목록을 **통째로 교체**하므로
  줄을 지우는 도중의 상태가 그대로 쓰이면 안 된다. (바로 옆 대응곡은 반대로 즉시
  반영한다 — 한 번에 하나이고 다시 붙이면 되돌려진다.)
- **번호를 문자열로 들고 있다.** 칸을 비울 수 있어야 하는데('번호 없음'), 숫자로 두면
  지우는 순간 0 이나 NaN 이 되어 **비운 것과 0번을 구분할 수 없다.**
- **＋ 목록에서 이미 쓴 곡집을 뺀다.** `song_entries` 의 기본키가
  `(song_id, songbook_id)` 라 같은 곡집을 두 번 넣으면 하나로 합쳐진다 — 넣을 수
  있게 두면 사라지는 줄이 생긴다.
- **번호 체계가 없는 곡집('기타')은 번호 칸 대신 '번호 없음'** 을 적는다. 서버가
  어차피 버리는 값이라, 넣을 수 있게 두면 넣었는데 사라진다.
- **다 빼면 경고를 띄운다** — 서버가 '기타' 로 떨어뜨리므로 곡이 사라지지는 않는다.
- **저장하면 왼쪽 목록도 다시 받는다.** 목록에 보이는 번호(`물42`)가 달라지는데,
  다시 찾지 않으면 방금 고친 것이 안 먹은 것처럼 보인다.

### 덤 — SongPanel 을 쪼갰다

붙이고 나니 `SongPanel.tsx` 가 **1,120줄**이 되어 이 프로젝트의 상한(800줄)을 넘었다.
수록·대응곡 두 줄을 `src/control/components/SongMetaRows.tsx` 로 떼어 냈다
(859 + 346). 이 둘은 곡 하나만 알면 되고 송출·가사 편집과 상태를 나누지 않아
경계가 깔끔하다.

두 곳에 복사돼 있던 `entryLabel` 도 `lib/plan-item-view.ts` 의 `shortEntryLabel` 로
합쳤다 — `songLabelOf`(제목 슬라이드용, `새찬송가 305장`)와 쓰임이 달라 이름을 나눴다.

**검증**: `tsc` · `vitest` 1,150개(신규 7개) · `vite build`.
격리 서버(7817) 브라우저 — '기타' 뿐이던 시험곡에 `많은물소리 42` 를 붙였다.
＋ 목록에서 방금 고른 곡집이 빠지고, 저장 후 제목 줄이 `많은물소리 42장 — …` 으로,
**왼쪽 목록 번호가 `—` → `물42`** 로 바뀌었다. 다 빼면 경고가 뜨고, 취소하면 DB 가

## 2026-09-03 — 템플릿 탭에서 못 바꾸던 글자 값 5개 (B)

`lineGapPx`(절대 행간) · `letterSpacing`(자간) · `opacity`(글자 투명도) ·
`bgBox`(글자 뒤 상자) · `textTransform`(대문자화).

**렌더는 전부터 되어 있었다.** `lib/template-css.ts` 가 CSS 변수로 내보내고
`public/output/output.css` 가 받아 쓰고 프리셋도 실제로 쓰고 있었다 — 투명도 0.75,
상자 `rgba(0,0,0,0.55)`, 절대 행간 16px. 그런데 템플릿 탭의 `StyleFields` 가
`TextStyle` 14개 중 **9개만** 편집시켜서, 이 다섯은 **JSON 내보내기/가져오기로만**
바꿀 수 있었다.

### 어디에 붙였나

| 값 | 자리 |
|---|---|
| 글자 투명도 | **모든 역할** (`simpleStyleVars` 도 `--*-opacity` 를 내보낸다). 20% 아래로는 못 내린다 — 0% 는 글자가 사라져 고장으로 보인다 |
| 줄 사이 고정 | 주·보조. 켜면 '줄 간격'(배수)이 잠기고 `고정 여백을 씁니다` 가 뜬다 — 둘이 함께 켜져 있으면 어느 쪽이 먹는지 알 수 없다 |
| 자간 · 대문자 · 글자 뒤 상자 | 주·보조의 `자간 · 대문자 · 글자 뒤 상자` 접이 안 |

**절 번호·참조·소제목에는 넷을 붙이지 않았다.** 그 셋은 `simpleStyleVars` 를 타서
`--*-spacing`·`--*-transform`·`--*-box-*` 가 **아예 나가지 않는다.** 컨트롤을 두면
만져도 화면이 안 바뀌는 칸이 된다. 단위 테스트로 이 경계를 못 박았다.

넷을 접이에 넣은 이유: 위쪽(글자 크기·색·외곽선)은 예배 준비마다 만지는 값이라 늘
펼쳐져 있어야 하고, 드물게 쓰는 것이 그 위에 끼면 그때마다 지나쳐야 한다.

### 만들다 찾은 함정 — `undefined` 로는 끌 수 없다

`lineGapPx` 를 `number | null` 로 바꿨다.

템플릿 저장은 초안을 **통째로** PUT 하고 서버가 얕게 병합한다(`mergeTemplate`).
`JSON.stringify` 는 `undefined` 키를 **지워 버리므로** 서버에는 그 필드가 아예 오지
않고, 옛 값이 그대로 남는다 — **화면에서 끌 수 없다.** 끄기는 `null` 이어야 한다.

단위 테스트에 함께 박았다: `null` 도 `undefined` 처럼 배수로 돌아가고,
**`0` 은 '여백 없음' 이라는 뜻이 있는 값이라 끈 것으로 보지 않는다.**

**검증**: `tsc` · `vitest` 1,143개(신규 5개) · `vite build`.
격리 서버(7816)에 출력 페이지를 따로 띄우고 **computed style 을 직접 읽어** 확인 —
`lineHeight 95.2px → 84px`(= 1em + 16px) · `letterSpacing 3px` · `opacity 0.6` ·
`textTransform uppercase` · `background rgba(0,0,0,0.55)` · `padding 14px 28px` ·
`radius 10px`. 저장 → 다시 읽기에서 `lineGapPx: 16` 이 남고, 끄고 저장하니
`lineGapPx: null` 이 남았다(옛 판이면 16 이 그대로 남는 자리다).
'원본 불러오기' 도 새 필드까지 되돌린다. 다크 모드 · 콘솔 오류 없음.

## 2026-09-03 — 예배 순서 네 가지: 탭 이동 · 찬양 검색 · 순서 저장 · 기본 설정

**요청**: ① 저장하지 않고 '찬양' 탭에 갔다 돌아오면 짜던 순서가 기본 유형으로
되돌아간다 ② '예배 순서'에서 「은혜」가 검색되지 않는다 (찬양 탭에서는 된다)
③ 불러온 순서를 고쳐 저장하는 길이 없다 — 이름을 정확히 맞혀 '덮어쓰기' 하는 것뿐이다
④ '기본 설정' 을 저장하는 버튼이 어느 것인지 모르겠다.

### ① 편집 초안을 담아 둔다

탭은 조건부 렌더다. '찬양' 을 누르는 순간 `PlanPanel` 이 언마운트되고 `useState` 가
전부 사라진다. 돌아오면 '아무것도 열지 않았으면 첫 유형을 연다' 규칙이 다시 돌아
**기본 유형이 들어찬다** — 짜 놓은 순서가 통째로 없어진다.

`sessionStorage` 에 초안(편집 중인 유형·항목·저장 여부·커서·펼친 항목)을 담고
첫 렌더에 되살린다 (`src/control/panels/plan-draft.ts`).

- 모듈 변수가 아니라 `sessionStorage` 인 이유: 브라우저 새로고침까지 견딘다.
  OBS 안내 배너를 보고 F5 를 누르는 일이 실제로 있다. 탭을 닫으면 비워진다 —
  '저장하지 않은 편집' 은 다음 예배까지 끌고 가면 안 되는 것이라 이 수명이 맞다.
- `useState(() => …)` 로 **첫 렌더에** 넣는다. effect 로 넣으면 그 사이에 기본 유형이
  들어찼다가 초안이 덮어써 화면이 한 번 튄다.
- 편집 중인 유형·회차를 **삭제하면 초안도 버린다** — 남겨 두면 지운 것이 되살아난다.
- 저장이 막힌 브라우저(시크릿 창·용량 초과)에서는 조용히 넘어간다. 초안을 못 담는
  것이 예배 진행을 막을 이유는 없다.

### ② 찬양 검색 — 잘려서 안 보였다

원인이 둘이었다.

1. **정렬**. 제목 검색이 가나다순이라 '은혜' 로 찾으면 제목이 정확히 「은혜」인 곡이
   34곡 중 **17번째**였다. **일치 등급 순**으로 바꿨다 — 완전일치 → 앞부분 → 포함,
   같은 등급 안에서는 짧은 제목이 먼저. 찬양 탭도 함께 좋아진다.
2. **개수**. 예배 순서 탭은 8개만 받아 왔다. 30개로 올렸다 (`SONG_HIT_LIMIT`).

`total` 도 고쳤다. 늘 `hits.length` 를 넘겨서 `truncated` 가 영원히 false 였고,
"34곡 중 8곡만 보임" 을 **아무도 알려 주지 않았다**. 제목·가사 일치 곡을 실제로
세어 넘긴다 (4,528곡·69,514줄에서 18ms 실측 — 200ms 디바운스 안).
후보 아래에 `656곡 중 30곡만 보입니다` 안내가 붙는다.

### ③ 불러온 순서를 그 자리에 저장한다

'순서 불러오기' 로 회차를 열어 고치면 **저장할 길이 없었다**. '순서 저장하기' 로
`2026-08-17 주일 1부 예배` 를 **똑같이 맞혀 쳐야** 덮어써졌고, 한 글자만 달라도
회차가 하나 더 생겼다. 화면에는 무엇을 열었는지도 안 나왔다 — 맨 위 칸이 유형만
담아서 저장된 순서를 열면 '— 예배 유형 —' 로 비었다.

- **맨 위 칸이 '지금 고치는 중인 것'** 이 됐다. `<optgroup>` 으로 예배 유형과 저장된
  순서를 함께 담는다 — 열어 둔 것의 이름이 늘 보이고, 거기서 바로 고를 수 있다.
- **버튼이 열어 둔 것을 따라간다.**

  | 열어 둔 것 | 2번 버튼 | 3번 버튼 |
  |---|---|---|
  | 예배 유형 | 템플릿 업데이트 | 순서 저장하기 |
  | 저장된 순서 | **저장하기** | **다른 이름으로 저장** |

- **`저장 안 됨` 줄이 어디에 남는지 말해 준다** — `저장 안 됨 — 저장하기 를 누르면
  '2026-08-17 주일 1부 예배' 순서에 남습니다`. 버튼 이름이 상황마다 달라지므로
  표시만 '저장 안 됨' 이면 어느 버튼인지 매번 헷갈린다.
- **⧉ ✎ ✕ 가 순서에도 걸린다.** 전에는 유형에만 걸려, 순서를 열면 셋이 모두 회색이라
  **이름을 고칠 길이 없었다** — '제목을 정확히 찾아 저장하기 어렵다' 던 것이 이것이다.
- '다른 이름으로 저장' 은 **원본 회차의 날짜를 물려받는다.** 오늘로 찍으면 지난주
  순서의 사본이 `2026-09-03 · 2026-08-17 주일 2부` 처럼 날짜 둘이 붙어 읽히지 않는다.

### ④ '기본 설정' 을 저장하는 버튼이 어느 것인지 몰랐다

기본 설정은 **따로 저장되는 것이 아니라 순서표 안에** 담긴다
(`service_plans.defaults`) — 그래서 저장 버튼도 위의 것 하나뿐이다. 동작은 맞았는데
안내가 `저장하기 를 눌러야 남습니다` 뿐이라, 그 버튼이 **순서**를 저장하는 것으로 보여
'기본 설정 저장 버튼' 을 찾게 됐다.

- **기본 설정 카드 맨 아래에 같은 버튼을 하나 더** 뒀다. 이름도 같다
  (`템플릿 업데이트` / `저장하기`). 설정을 만진 자리에서 그대로 누른다.
- 그 옆에 지금 상태를 적는다 — `아직 저장되지 않았습니다` / `지금은 '주일예배' 에
  저장된 상태입니다`. 바꾼 것이 있으면 버튼이 파랗게 켜진다.
- 버튼 이름을 `saveLabel` 한 곳에서 만든다. 안내 문구가 **화면에 없는 버튼 이름**을
  가리키는 일이 생기지 않게.

**함께 고친 것 — 이름을 바꾸면 저장하지 않은 기본 설정이 사라졌다.**
'이름 바꾸기' 는 일부러 항목을 보내지 않는다(저장하지 않은 편집을 굳히면 안 되므로).
그런데 서버가 돌려주는 plan 을 그대로 받아 써서, **저장된** 기본 설정이 편집 중인 것을
덮었다. `items` 는 별도 state 라 살아남는데 `defaults` 만 없어져, `저장 안 됨` 이 떠 있는
채로 방금 고른 역본이 옛 값으로 돌아갔다. 이름만 갈아 끼우도록 고쳤다.

**검증**: `tsc` · `vitest` 1,116개(신규 16개) · `vite build`.
격리 서버(7810)에 실제 곡 4,528개를 넣고 브라우저로 —
「은혜」가 후보 1번, `656곡 중 30곡만 보입니다` 안내, 항목을 넣고 '찬양' 탭에 갔다

## 2026-08-20 (밤, 후속 2) — 저장해도 인용구가 남는다 · 프로젝터 순서 표시 글자 통일

**사용자 지적 두 가지.**

### ① 저장하면 인용구가 성경 항목으로 되돌아갔다 (버그)

> 인용구로 추가한 후에 '템플릿 업데이트' 를 클릭하면 인용구들이 모두 '성경' 처럼
> 타이틀과 본문으로 바뀐다. 매주 미리 준비한 후에 '템플릿 업데이트' 로 저장을
> 대신해서 쓸 것 같은데, 인용구가 바뀌어 버리면 인용구로 쓴 의미가 없어진다.

원인은 저장 경로의 **화이트리스트**다. `normalizeItems` 는 아는 필드만 하나씩 옮겨
담고 나머지는 버린다 — 모르는 쓰레기가 순서표에 박히지 않게 하는 옳은 설계다. 그런데
인용구를 만들면서 거기에 `quote`·`preview` 를 **더하지 않았다.** 화면에서는 잘 보였으므로
저장하기 전까지 알 수 없었다.

고친 것: 그 두 필드를 화이트리스트에 넣었다.

| 규칙 | 왜 |
|---|---|
| `quote` 는 **`true` 만** 받는다 | `'yes'` 같은 값이 박히면 판정이 흐려진다 |
| `preview` 는 **인용구일 때만** 담는다 | 본문 낭독에는 쓰이지 않는다 — 뜻 없는 값을 남기지 않는다 |
| `preview` 는 길이를 잘라 담는다 | 라벨이다 (`PREVIEW_MAX`) |

**같은 부류의 버그를 막는 테스트를 만들었다** — `tests/integration/plan-item-roundtrip.test.ts`.
종류마다 **모든 선택 필드를 채운 항목**을 저장 경로에 통과시켜 하나도 빠지지 않았는지
본다. 새 필드를 넣고 그곳을 잊으면 실패한다. 나머지 다섯 종류(성경·찬양·교독문·순서
표시·전례문)를 대조했고 빠진 것은 없었다.

### ② 프로젝터의 순서 표시 글자 크기를 고르게

> 프로젝터 화면의 '예배 순서' 표시는 글자 크기를 리듬있게 하지 말고 첫 글자의 크기로
> 동일하게 해줘.

대비가 낮은 프로젝터에서는 작아진 글자가 먼저 뭉개진다. 두 곳을 막았다.

| 무엇 | 어디서 |
|---|---|
| 자동 리듬 | `projectorTemplate()` 이 `titleRhythm: 0`, `titleRhythmY: 0` 을 **명시한다** |
| **손으로 맞춘 글자별 조정** | `projector.css` 가 `.rhythm-char` 의 인라인 크기를 되돌린다 |

자동 리듬은 '전체' 프리셋에 설정이 없어 이미 0 이었다(`clampRhythm(undefined)`).
그래도 명시한 이유: 나중에 그 템플릿에 리듬을 넣어도 프로젝터는 고르게 남는다.

진짜 원인은 **수동 조정**이었다 — 사용자 순서표의 `찬양과경배` 에 글자별 크기가
`0.8`·`0.9` 로 박혀 있었다. 그것은 항목에 담겨 있고 렌더러가 **인라인**으로 꽂으므로
템플릿으로 막을 수 없다. CSS 로 덮었다. 인라인을 이기려면 `!important` 뿐이고,
**렌더러가 만든 표시용 인라인을 표시 전용 화면에서 되돌리는** 이 자리가 그것이 옳은
경우다 (색·크기처럼 CSS 변수로 되는 것은 `body` 선언으로 처리했다 — 이것만 예외다).

`1em` 은 부모 글자 크기 = **첫 글자의 크기**다 (리듬 표의 첫 칸이 `1.0`).

### 실측

| 확인 | 결과 |
|---|---|
| 인용구 넣고 '템플릿 업데이트' | 두 줄 모두 그대로 (`고전 1:3 …`, `고전 1:4 …`) |
| DB | `quote: true` · `preview` · `paging: 'verse'` 살아 있음 · 일반 성경 항목과 구분됨 |
| 프로젝터 | 인라인이 `0.8em`·`0.9em` 인데 **실제 크기는 다섯 글자 모두 96px** · 이동 `none` |
| OBS(미리보기) | `120 · 115.2 · 96 · 108 · 108px` — **리듬 그대로** |
| 테스트 | 909개 통과 (왕복 10개 · 프로젝터 4개 추가) |

## 2026-08-20 (밤, 후속) — 인용구가 네 화면에서 같은 글로 나온다

**사용자 지적**: 인용구를 실행하면 네 화면의 말씀 형식이 모두 다르다.

```
관리자      고전 1:3 하나님 우리 아버지와…
OBS         고전 1:3 ⏎ 3 하나님 우리 아버지와…
강사 모니터   3 하나님 우리 아버지와… ⏎ 고전 1:3
프로젝터     하나님 우리 아버지와…
```

### 왜 넷이 달랐나

네 화면이 **서로 다른 렌더러**를 쓰고 참조·절 번호 규칙이 제각각이었다.

| 화면 | 규칙 |
|---|---|
| 관리자 목록 | `describeItem` 이 참조 뒤에 미리보기를 붙인다 |
| OBS | 참조를 **별도 줄**(`#reference`)로 위/아래에 그리고 절 번호를 붙인다 |
| 강사 모니터 | 절 번호를 **늘** 붙이고(설정을 보지 않았다) 참조를 아래에 붙인다 |
| 프로젝터 | '전체' 템플릿이 참조·절 번호를 **둘 다 끈다** |

`showReference: 'inline'` 이라는 값은 타입에 있었지만 **구현이 없었다** — `'none'` 이
아니면 무조건 별도 줄이었다.

### 참조를 **본문 글자에 넣었다**

참조를 별개 요소로 두는 한 렌더러 셋을 각각 고쳐야 하고, 프로젝터는 템플릿이 참조를
끄므로 예외가 또 필요하다. **규칙이 넷이면 넷은 다시 어긋난다.**

글자로 넣으면 네 화면이 그것을 '본문' 으로 받으므로 어긋날 자리가 **구조적으로**
없어진다. 접두사는 **항목의 `ref`** 를 쓴다 — 목록 줄과 글자까지 같아진다
(서버가 주는 `slide.reference` 는 정식 이름 `고린도전서 1:3` 이라 목록과 달라진다).

DB 는 손대지 않는다. 화면에 보낼 **사본**을 만든다 (`quoteSlides` 는 불변이다).

### 함께 끈 것

| 무엇 | 왜 |
|---|---|
| 절 번호 | `고전 1:3` 에 이미 절이 있다 — 안 끄면 `고전 1:3 3 하나님…` |
| 별도 참조 줄 | 붙였는데 아래에도 나오면 같은 것이 두 번 나간다 |
| 보조 역본 접두사 | 붙이지 **않는다** — 참조가 두 번 보인다 |

항목의 **참조 표기를 `끔`** 으로 두면 접두사를 붙이지 않는다 — 그 토글이 인용구에서도
뜻을 갖는다.

### 강사 모니터가 설정을 따르게 했다

`stage.js` 가 절 번호를 **늘** 붙이고 있었다(`verse.verse + ' ' + verse.text`).
`display.verseNumbers === false` 를 보게 했다. 이 파일은 의존성 0 이라 규칙을 두 곳에
적게 되므로 `tests/unit/quote-consistency.test.ts` 가 **파일을 읽어** 묶어 둔다.

### 📖 성경(본문 낭독)은 조금도 바뀌지 않았다

`resolveItem` 이 `item.quote` 일 때만 이 변환을 부른다. 실측으로 확인했다 —
`창 1:1-6` 은 절 번호 `1`, 참조 줄 `창 1:1-6`, 보조 역본까지 예전 그대로다.

### 실측 (네 화면 동시)

| 화면 | 나온 글 |
|---|---|
| 관리자 목록 | `고전 1:3 하나님 우리 아버지와 주 예수 그리스도로부터 은혜와 평강이 있기를 원하노라` |
| OBS(미리보기) | 같음 · 참조 줄 없음 · 절 번호 없음 |
| 강사 모니터 | 같음 (한 줄) |
| 프로젝터 | 같음 · 참조 줄 없음 · 절 번호 없음 |
| 성경 낭독 대조 | `1태초에 하나님이…` + `1In the beginning…` · 참조 줄 `창 1:1-6` — **그대로** |
| 테스트 | 895개 통과 (`verse-quotes` 9개 · `quote-consistency` 9개 추가) |

> 화면마다 옛 판이 떠 있으면 여전히 다르게 보인다 — 그 창을 새로고침해야 한다
> (TROUBLESHOOTING §2.4.13).

## 2026-08-20 (밤) — 인용구를 '성경 절 낱개'로 바꿨다

**요청**: 광고와 인용구가 기능이 겹친다. 인용구는 성경 본문을 **카테고리가 아닌 개별
슬라이드로** 가져오는 기능으로 바꾼다. 성경에서 `창 1:1-6` 은 '창 1:1-6' 타이틀 밑에
6절이 들리지만, 인용구에서는 **타이틀 없이** 창 1:1 … 창 1:6 이 나온다.

### 겹쳐 있던 것이 맞았다

광고와 인용구는 화면에서 **똑같이 그려졌다**(둘 다 `kind: 'text'`). 실제 차이는
아이콘과 `↩ 직전으로` 뿐이었다. 그리고 사용자가 갖고 있던 인용구 항목의 내용이
바로 **`창 3:15`** 였다 — 이미 참조를 인용구로 쓰려 했고, 지금은 글자 그대로 화면에
나갔다. 요청과 정확히 맞는 증거였다.

### 무엇이 바뀌었나

| | 📖 성경 | 💬 인용구 |
|---|---|---|
| `창 1:1-6` | 항목 **하나** | 항목 **여섯** (`창 1:1` … `창 1:6`) |
| 목록 줄 | 머리 줄 + 펼치면 6장 | 여섯 줄, 각 줄에 **본문 함께** |
| 펼치기 | `▸` 로 장을 고른다 | 없다 — **한 번 클릭으로 송출** |
| 제목 슬라이드 | 참조가 먼저 나간다 | **나가지 않는다** |
| `↩ 직전으로` | 없음 | 있음 (유지) |

### 성경 항목과 **같은 구조**로 담았다

인용구도 `type: 'bible'` 이고 `quote: true` 표시만 다르다. 자유 글자로 담으면 역본을
바꿀 수 없고 본문이 순서표에 복사된다. 같은 구조로 두면 역본·참조 표기·절 번호·글꼴·
템플릿이 **그대로** 쓰이고, **본문은 언제나 DB 가 원본**이다.

### 목록 줄의 본문은 항목이 담는다

`창 1:1 태초에 하나님이 천지를 창조하시니라` 처럼 보여 달라는 요청이었다. 그런데
컨트롤 패널은 **펼친 항목 하나만** 본문을 조회한다(`resolveItem`) — 낱개로 흩어진
여섯 줄의 본문을 조회 없이 그릴 방법이 없다. 그래서 `preview` 를 항목에 담는다
(`songTitle`·`readingTitle` 과 같은 이유).

**라벨일 뿐이다.** 화면에 나가는 본문은 언제나 DB 에서 다시 읽으므로 잘려 있어도 되고
없어도 된다(없으면 참조만 보인다). 역본을 바꾸면 새 역본으로 다시 읽는다.

### 막은 버그 두 개

- **비동기 뒤의 덮어쓰기**: 역본을 바꾼 직후 미리보기를 다시 읽는 경로가 옛 `items`
  배열로 덮어써 **역본 변경을 되돌렸다.** `patchItems` 가 함수형 갱신을 받게 하고
  그 경로를 함수형으로 바꿨다. 항목을 여러 개 넣는 `insertItems` 도 같게 했다 —
  자리는 어긋나도 되지만 항목이 사라지면 안 된다.
- **한 번에 여러 개**: `insertItem` 을 여섯 번 부르면 `items` 가 이 렌더의 값이라
  마지막 하나만 남는다. `insertItems` 로 한 번에 넣는다.

### 옛 항목

옛 자유 글자 인용구는 **그대로 나간다**(광고처럼 글자가 뜬다). 새로 만들 수만 없다.
사용자의 한 건(`창 3:15`)은 요청에 따라 지웠다 — `scripts/remove-text-quotes.ts`
(미리보기 기본 · 무엇을 지울지 내용까지 보여 준다 · `--apply` 가 스냅샷을 먼저 뜬다).

### 실측

| 확인 | 결과 |
|---|---|
| `창 1:1-6` 넣기 | 6줄 · `인용구 6개를 넣었습니다 — 창 1:1-6` |
| 목록 줄 | `창 1:1 태초에 하나님이 천지를 창조하시니라` (요청한 모양) |
| 펼치기 | 인용구 줄에 `▸` 없음 · 성경 줄에는 있음 |
| 한 번 클릭 | 제목 없이 `4빛이 하나님이 보시기에 좋았더라…` 가 바로 나갔다 |
| `↩ 직전으로` | `(순서 표시)` 로 뜨고, 누르면 설교 화면으로 돌아왔다 |
| 역본 바꾸기 | 목록 줄이 `창 1:2 Now the earth was formless…` 로 다시 읽혔다 |
| 실제 데이터 | 옛 인용구 1개 삭제 · 주일예배 22 → 21개 · 순서 표시 8개 그대로 |
| 테스트 | 877개 통과 (`verse-quotes` 17개 추가) |

## 2026-08-20 (저녁) — 프로젝터: 주소줄을 실제로 없애기

**사용자 재요청**: 스크린샷으로 제목줄('프로젝터 — Sermon Presentation')과
출처줄('127.0.0.1:7777/projector/')을 빨간 박스로 표시하며 "없앨 수 없나".

### 기능은 있었지만 **찾을 수 없었다**

전체 화면(`F`)이 이미 있었는데 도달하지 못했다. 원인은 둘로 본다 — `F` 를 눌러야 하는
것을 몰랐거나, **키보드 초점이 브라우저 쪽에 있어서** `F` 가 페이지에 닿지 않았다.
창을 열고 바로 누르면 실제로 그렇게 된다. 둘 다 **클릭**으로 풀린다.

| 무엇 | 왜 |
|---|---|
| **화면을 클릭하면 전체 화면** | 가장 찾기 쉬운 동작. 클릭은 초점도 함께 가져온다 |
| 클릭으로 **나가지는 않는다** | 예배 중 실수로 벽에 브라우저 창이 드러나면 안 된다 |
| 막대를 누른 클릭은 제외 | `+` 를 누르려다 전체 화면이 되면 안 된다 |
| **전체 화면 선택을 기억한다** | 다음에 열면 첫 클릭·키 입력에서 저절로 들어간다 |
| 마우스 이동은 세지 않는다 | 브라우저가 사용자 동작으로 인정하지 않아 거절되고, 기회를 잃는다 |
| 사람이 직접 나가면 기억을 끈다 | 창 모드로 쓰겠다는 뜻이다 |
| 안내는 전체 화면이 아닐 때만, 막대와 함께 | 상시 표시하면 프로젝터 번인 위험 |

### '앱으로 설치' 를 붙였다 (PWA)

매주 쓰는 화면이라면 설치판이 `F` 보다 편하다 — **애초에 주소줄이 없는 창**으로 열리고,
`display: fullscreen` 이라 처음부터 전체 화면으로 뜬다. 클릭조차 필요 없다.

아이콘 PNG(192·512)는 **코드로 그린다** — `scripts/make-projector-icons.ts` 가
`node:zlib` 만으로 만든다. 이미지 도구를 깔지 않아도 되고, 무엇을 그렸는지 읽어서 알 수
있다(바이너리는 diff 가 되지 않는다). 검은 바탕에 흰 가로 막대 셋 — 벽에 비친 글줄.

설정 탭에 **프로젝터로 띄우기** 카드를 넣었다. 방법을 **찾을 수 있는 자리**가 필요했다.

### 실측

| 확인 | 결과 |
|---|---|
| 매니페스트 | `200 · application/manifest+json` · `display: fullscreen` · 아이콘 2개 |
| 아이콘 | 530 B / 1,939 B · PNG 서명 확인 |

| 테스트 | 860개 통과 (`projector-page` 7개 추가) |

### OBS 와 **동시에 다른 배치**를 쓴다

이것이 핵심이다. 카메라 영상 위에는 '하단 두 줄'로 나가면서, 같은 내용이 프로젝터에는

|---|---|
| OBS 송출 | 활성 템플릿 (예: 하단 두 줄) |
| 프로젝터 | **'전체 — 성경·찬송 겸용'** 고정 |

`server/ws.ts` 의 `templateFor()` 가 `projector` layer 에만 다른 템플릿을 보낸다.
`getTemplateOrDefault(-8)` 를 거치므로 **'전체' 프리셋을 고치면 프로젝터도 따라간다** —
눈에 보이지 않는 별도 설정을 만들지 않았다. 다른 템플릿을 편집하는 중에 뿌리는
`style:set` 은 프로젝터에 보내지 않는다 (벽에 비친 글이 춤추면 안 된다).

### 렌더러를 복제하지 않았다

`output.js` 는 1044줄이고 성경·찬양·교독문·전례문 렌더러가 모두 들어 있다. 프로젝터
페이지는 **같은 DOM id** 를 두고 같은 CSS·같은 스크립트를 불러온다. `projector.css`/
`projector.js` 는 덧칠만 한다. `tests/unit/projector-page.test.ts` 가 파일을 읽어
이 규칙을 지킨다.

`output.js` 는 `location.pathname` 이 `/projector` 로 시작하면 layer 를 스스로 정한다 —
쿼리에 맡기면 즐겨찾기에서 빠졌을 때 OBS 화면으로 집계된다.

### 서버 패치와 싸우지 않는다

서버의 `style:patch` 는 CSS 변수를 `<html>` 인라인에 꽂는다. 그런데 **CSS 변수는
상속으로 결정된다** — 값을 읽는 쪽에서 가장 가까운 조상이 이긴다. `body` 가 `html` 보다
가까우므로 `body.projector { --primary-color: … }` 가 서버 패치를 가린다.
`!important` 도, 인라인을 지우는 짓도 필요 없다.

### autoFit 을 껐다

키우면 넘치고, 넘치니 되돌려 깎아서 **글자 크기가 안 바뀌는 것처럼 보인다** —

| 곳 | 내용 |
|---|---|

고정이라, 글자를 키워도 줄 간격이 함께 부풀지 않고 겹치지도 않는다. 상대 배수는 키울 때
간격이 벌어지고, 순수 px 는 키울 때 겹친다.

**측정 주의**: 출력 무대는 창 크기를 따라간다. 720p 창에서는 자동 축소가 최소 배율(0.6)까지
내려가 크기 증가를 상쇄하므로, 실측은 **1920×1080** 에서 해야 한다.

## 이 프로젝트가 일하는 방식 (짧게)

- **추측 말고 실측.** 판단은 측정에서 나온다 — ESV 판본 비교, 운율 순위 규칙,
  폰트 대체 비율, 스크롤바 폭, 글자 크기 배수까지 브라우저에서 재고 정했다.
- **화면을 스스로 비우지 않는다.** 서버가 죽어도 출력은 마지막 내용을 유지한다.
- **자동 결과는 제안이다.** 사람이 승인해야 확정되고, 승인한 것은 자동이 건드리지 않는다.
- **되돌릴 수 없는 일 앞에는 백업과 미리보기.**
- 검증 3종은 항상 통과: `npx tsc --noEmit && npx vitest run && npx vite build`
  (2026-08-16 기준 **556개 통과**)
