**G3 가 유일한 실질 미달**입니다. 한/영 병기는 사용자의 상시 요구사항인데(미국 한인교회)
2언어를 넣을 **데이터가 없습니다.** 구조만 있고 내용이 없는 상태가 오래 유지되고 있습니다.

### 1.2 범위 이탈 — 이것이 핵심입니다

기획서 §1.3 「범위에서 제외」 첫 줄:

> **영상/이미지 배경 재생 (OBS가 이미 잘 함 — 우리는 텍스트 레이어만 담당)**

그런데 지금:

| 구현물 | 줄 수 |
|---|---|
| `server/routes/backgrounds.ts` (업로드·삭제·총량 상한) | 277 |
| `src/control/components/BackgroundPicker.tsx` | 238 |
| 출력 페이지의 배경·동영상 렌더 + 자동 재생 재시도 | ~120 |
| 항목 배경(`ItemBackground`) + 검증 + 테스트 | ~250 |
| 예배 전 안내 `media` 항목 | ~150 |
| **합계** | **약 1,035줄** |

여기에 제가 최근에 만든 **보안 조치 S-1**(총량 상한·삭제 API·409 보호)이 붙어 있습니다.
그 보안 위험 자체가 **범위 밖 기능이 만들어낸 것**입니다 — 업로드 기능이 없으면
디스크 고갈 위험도 없었습니다.

**사용자의 직감이 맞습니다.** "배경 그림, 미디어는 OBS에서 하는 것이 훨씬 편할 것 같다" 는
기획서가 처음에 내린 판단과 같습니다. 중간에 요구가 들어오면서(제가 그대로 구현했습니다)
방향이 흐려졌습니다.

## 2. OBS 기반 vs Standalone — 판단

### 2.1 각각이 실제로 무엇을 뜻하는가

| | OBS 기반 (현재) | Standalone |
|---|---|---|
| 화면 출력 | OBS 브라우저 소스 → OBS 가 스크린/스트림에 합성 | 앱이 직접 전체화면 창을 띄운다 |
| 배경·미디어 | **OBS 소스로 깐다** (레이어·전환·크로마키·필터 전부 무료) | 앱이 직접 만들어야 한다 |
| 카메라 합성·녹화·송출 | OBS 가 한다 | 불가능 (또는 다시 만들어야 한다) |
| 2개 모니터 다른 내용 | OBS 씬 2개 + 브라우저 소스 2개 | 앱 창 2개 |
| 조작자 학습 부담 | OBS 를 알아야 한다 | 앱만 알면 된다 |
| 우리가 만들 코드 | **텍스트 레이어만** | 전체 프레젠테이션 엔진 |

### 2.2 지금 프로젝트가 있는 곳

**둘 사이에 어중간하게 걸쳐 있습니다.** 텍스트 레이어(OBS 전제)로 시작해서, standalone
기능(배경·미디어·자동 재생)을 덧붙였습니다. 그 결과:

- 배경을 **두 곳에서** 지정할 수 있습니다 — OBS 소스와 우리 앱. 어느 쪽이 위에 오는지
  조작자가 알기 어렵습니다
- 제가 실제로 그 혼선에서 나온 버그를 고쳤습니다: **배경을 정하는 코드가 세 군데** 있어서
  도착 순서에 따라 결과가 달라졌고, 출력 페이지를 새로 열면 배경이 사라졌습니다(3.23)
- 동영상 자동 재생이 막히면 첫 프레임에서 얼어붙는 문제도 같은 뿌리입니다. **OBS 미디어
  소스는 이런 문제가 아예 없습니다**

### 2.3 권고: OBS 기반 유지 + 범위를 다시 좁힌다

**이유 셋:**

1. **비교 우위가 텍스트에 있습니다.** 이 프로젝트가 잘하는 것은 OBS 가 절대 못 하는
   것입니다 — 12역본 성경 조회, 4,396곡 가사 검색, 운율 맞춘 줄나눔, 교독문 인도자/회중
   짝 맞추기, 예배 순서 큐. 배경 재생은 OBS 가 이미 우리보다 잘합니다.
2. **standalone 은 새로운 큰 짐을 집니다.** 화면 관리, 다중 디스플레이, 전환 효과,
   미디어 코덱, 하드웨어 가속... 그리고 카메라 합성·녹화·유튜브 송출을 포기하거나
   다시 만들어야 합니다. 교회 예배는 대개 **송출도 함께** 합니다.
3. **지금 코드가 이미 OBS 전제로 최적화돼 있습니다.** 출력 페이지 의존성 0, 알파 투명,
   CSS 변수 즉시 반영 — standalone 으로 가도 이 자산은 그대로 쓰지만, 반대로
   standalone 을 위해 만든 것(배경·미디어)은 OBS 에서 **빼야 할 것**입니다.

**단, 하나 예외가 있습니다** — 아래 2.4.

### 2.4 예외: '강사 모니터' 는 standalone 성격이다

2개 모니터 요구(강단 청중용 / 강사 모니터용)는 **성격이 다릅니다.**

- 청중용: OBS 로 나간다 (배경·카메라와 합성)
- **강사용: OBS 를 거칠 이유가 없다.** 강사에게 필요한 것은 "지금 화면 + 다음 화면 +
  남은 시간 + 설교 노트" 같은 **조작자용 정보**입니다. 이건 브라우저 창 하나를 강사
  모니터에 전체화면으로 띄우면 끝입니다

즉 **OBS 기반을 유지하면서도 2개 모니터가 됩니다.** 강사용은 우리 앱이 직접 띄우는
별도 페이지(`/stage`)로 만들면 됩니다. 이것이 업계 표준이기도 합니다(ProPresenter 의
Stage Display, EasyWorship 의 Foldback).

## 3. 2개 모니터 — 지금 구조로 무엇이 되고 안 되나

### 3.1 실측한 현재 상태

`layer` 라는 개념이 **이미 있습니다**:

- 출력 페이지가 `?layer=main` 으로 접속하고 `hello` 에 실어 보냅니다
- 서버가 클라이언트별로 `layer` 를 기억합니다
- `layer !== 'preview'` 인 것만 '출력 연결됨' 으로 셉니다

**그런데 상태를 layer 별로 나눠 보내지 않습니다.** `broadcast({ t: 'state', ... })` 는
역할(control/output)로만 거르고 layer 는 보지 않습니다. 그래서:

> 지금 브라우저 소스를 두 개 열면 **똑같은 화면이 두 개** 나옵니다.
> 강단용과 강사용을 다르게 만들 수 없습니다.

### 3.2 필요한 작업 (추정)

| 할 일 | 크기 |
|---|---|
| `broadcast` 가 layer 를 거르게 한다 | 작다 (10줄 내외) |
| 강사용 페이지 `/stage` — 지금 화면·다음 화면·항목 목록·경과 시간 | 중간 (새 페이지 하나, 출력 페이지 재사용 가능) |
| 컨트롤 패널에 '강사 모니터 열기' 버튼 | 작다 |
| 강사용은 **템플릿을 따르지 않는다** (읽기 편한 고정 스타일) | 작다 |

**핵심은 서버 변경이 작다는 것입니다.** `layer` 를 미리 넣어 둔 것이 여기서 값을 합니다.

## 4. 맥·윈도우 빌드 (Electron) — 장애물 점검

### 4.1 좋은 상태

| 항목 | 상태 |
|---|---|
| 네이티브 모듈 | **0개.** `node:sqlite` 내장만 쓴다 (기획서 D1 의 판단이 여기서 값을 한다) |
| 런타임 의존성 | 6개뿐 (fastify, @fastify/static, ws, react, react-dom, pino-pretty) |
| 포트 충돌 | 자동 탐색 있음 (`PORT_SCAN_RANGE = 20`) |
| 데이터 경로 | `SERMON_DATA_DIR` 로 갈아끼울 수 있게 이미 설계돼 있다 |
| 빌드 산출물 | `public/app/` 정적 파일 — Electron 이 그대로 로드 |

### 4.2 남은 장애물

| 문제 | 크기 | 비고 |
|---|---|---|
| **원본 폴더 경로 가정 2곳** — `~/Desktop/Data/BibleDB`, `~/Desktop/Data/Background` | 작다 | 윈도우에서 `Desktop` 이 OneDrive 아래일 수 있다. 첫 실행 때 폴더를 **고르게** 해야 한다 |
| **성경 DB 102MB 를 어떻게 배포하나** | **중간~크다** | 앱에 넣으면 설치 파일이 100MB 넘고, 넣지 않으면 사용자가 원본 12개 파일을 구해 빌드해야 한다 |
| 첫 실행 안내(성경 DB 없음 → 무엇을 할지) | 작다 | 지금은 빨간 배너만 뜬다 |
| 자동 업데이트 | 중간 | 봉사자 PC 여러 대면 필요해진다 |
| 코드 서명·공증 | 중간 | 맥은 공증 없으면 "확인되지 않은 개발자" 경고. 윈도우는 SmartScreen |

**가장 큰 결정은 성경 DB 배포입니다.** 세 갈래:

1. 앱에 넣는다 → 설치 파일 ~130MB. 가장 편하다
2. 첫 실행 때 내려받는다 → 인터넷 필요. 오프라인 100% 목표(G6)와 충돌
3. 사용자가 원본을 갖고 있다고 전제한다 → 현재 방식. 다른 봉사자에게 배포 불가

**권고: 1번.** 130MB 는 요즘 기준 크지 않고, G6(오프라인)와 "봉사자 PC 설치"를 동시에
만족하는 유일한 길입니다.

| 찬양 | 544 | 2 | 0 | 3 |

성경 넣기, 찬양 찾아 넣기, 가사 표시 설정, 템플릿 지정, 배경 지정, 교독문·전례문 편집.

### 5.2 진단: 특화가 아니라 **한 탭이 다 흡수했다**

원래 설계(기획서 §6.1)는 성경·찬양·템플릿을 각각의 작업 공간으로 두고 예배 순서를
'조립' 공간으로 뒀습니다. 실제로는:

- **예배 순서** = 조립 + 진행 + 편집 (사실상 앱 전체)
- **성경** = 참조 검색기 (예배 순서에서도 되므로 존재 이유가 약하다)
- **찬양** = 곡 검색·가사 편집기 (편집은 여기만 되므로 이유가 있다)
- **검토** = 줄나눔 승인 (별개 작업이라 이유가 분명하다)
- **템플릿** = 스타일 편집 (이유가 분명하다)
- **곡집 관리** = 가져오기 (이유가 분명하다)

즉 **성경 탭이 가장 애매합니다.** 그리고 예배 순서 탭은 **너무 큽니다** — 2,620줄 한 파일에
7종 항목 편집 + 자동 진행 + 템플릿 + 배경 + 유형 관리가 다 들어 있습니다.

### 5.3 권고

| 대상 | 권고 |
|---|---|
| 예배 순서 탭 | **쪼갠다.** 항목 종류별 편집 칸을 별도 컴포넌트로 (`items/BibleItem.tsx` 등). 지금은 한 파일이라 한 곳을 고치면 다른 항목이 깨질 수 있고, 실제로 그런 버그를 여러 번 고쳤다 |
| 성경 탭 | **남긴다. 단 목적을 좁힌다** — '설교 중 즉석 조회'. 예배 순서에 없는 구절을 급히 띄우는 용도라면 이유가 분명하다. 지금은 그 목적이 UI 에 드러나지 않는다 |
| 찬양·검토·템플릿·곡집 | 유지. 각각 이유가 분명하다 |
| 새로 필요한 것 | **강사 모니터(`/stage`)** — 탭이 아니라 별도 창 |

## 6. 지금 덜어낼 것 / 더할 것

### 6.1 OBS 기반을 확정한다면 — 덜어낼 것

| 대상 | 줄 수 | 왜 |
|---|---:|---|
| 배경 **업로드** API + 총량 상한 + 삭제 | ~380 | OBS 소스로 깔면 필요 없다. **보안 위험 S-1 도 함께 사라진다** |
| `BackgroundPicker` 의 업로드 부분 | ~120 | 폴더에서 고르기만 남긴다 |
| 예배 전 안내 `media` 항목 (그림·동영상) | ~150 | OBS 씬 하나로 훨씬 잘 된다 |
| 동영상 배경 + 자동 재생 재시도 | ~90 | OBS 미디어 소스가 문제없이 한다 |
| **합계** | **~740** | |

**남길 것**: 교독문·전례문의 **항목 배경**(`ItemBackground`). 이건 OBS 로 대체하기 어렵습니다 —
순서 항목마다 배경이 바뀌어야 하는데, OBS 로 하면 씬을 항목 수만큼 만들어야 합니다.
지금처럼 **폴더에서 고르기만** 남기고 업로드·삭제·상한은 덜어냅니다.

> 즉 "배경은 OBS 가" 를 100% 적용하면 안 됩니다. **정적 배경 = OBS · 항목별로 바뀌는
> 배경 = 우리** 가 맞는 경계입니다.

## 7. 불안요소 (현재)

### 7.1 UI 테스트가 0 — **가장 큰 위험**

| 영역 | 커버리지 |
|---|---|
| `lib/` | **94.95%** |
| `server/routes/` | 80.75% |
| `server/db/` | 73.02% |
| `server/` (app·ws·index) | 44.19% |
| **`src/` (React UI)** | **측정 안 됨 = 테스트 없음** |
| e2e | **없음** |

순수 로직은 훌륭합니다. 그런데 **사용자가 실제로 만지는 2,620줄 패널에 회귀 테스트가
없습니다.** 이 세션에서만 UI 버그를 여러 개 고쳤습니다:

- 새 항목이 맨 끝에 붙던 문제(줄 번호 ≠ 항목 번호)
- 판본 토글이 미리보기를 갱신하지 않던 문제
- 배경이 세 곳에서 결정되던 문제
- 후보 40개가 패널을 넘치던 문제
- 기본 설정을 열었을 때 배경 목록이 비던 문제

**전부 제가 브라우저로 눌러 보다가 발견했습니다.** 다음에 누가 고치면 같은 것이 다시
깨질 수 있고, 그때는 예배 중에 발견합니다.

### 7.2 검토 대기 4,387곡 — 설계가 규모를 못 견딘다

| 지표 | 값 |
|---|---|
| 전체 곡 | 4,396 |
| 승인됨 | **9** |
| 대기 | **4,387** |
| 손봐야 할 곡(`needsAttention`) | **1,506** |

'검토' 탭은 **한 곡씩 눈으로 보고 승인**하는 설계입니다. 1,202곡일 때는 성립했지만
4,396곡에서는 산술적으로 불가능합니다(하루 50곡씩 봐도 88일).

이건 기능 결함이 아니라 **설계 전제가 규모에 안 맞는** 문제입니다. 방향을 정해야 합니다:

- **(a) 쓰는 곡만 검토한다** — 예배 순서에 넣는 순간 검토 대기 상단으로 올린다.
  실제로 쓰는 곡은 연간 100~200곡이다. **가장 현실적이다**
- (b) 곡집 단위로 일괄 승인 — 빠르지만 줄나눔 오류가 예배에 그대로 나간다
- (c) 대기열을 그냥 둔다 — 지표가 무의미해지고 '승인' 표시의 뜻이 사라진다

### 7.3 그 밖

| 항목 | 위험 | 상태 |
|---|---|---|
| 원본 번호 충돌 35건 | 낮음 | 리포트로 알렸다. 번호로 찾으면 둘이 나온다 |
| 한/영 병기 데이터 없음 | 중간 | G3 미달. 상시 요구사항 |
| 접속 암호·요청 수 제한 | 낮음(현재) | 랜을 열면 즉시 필수 (보드 5·6 보류) |

| 브라우저 자동화로 Enter 키·타이머 검증 불가 | 낮음 | 이 세션에서 겪었다. 순수 함수로 빼서 단위 테스트로 대체 중 |

### 8.3 덜어내기를 권하는 이유를 한 번 더

지금 프로젝트에서 **가장 복잡하고 버그가 많이 나온 부분이 범위 밖 기능**입니다.
배경 하나 때문에:

- 보안 위험 하나(S-1)를 만들고 막았다
- 배경 결정 지점이 세 곳으로 흩어져 출력 페이지를 새로 열면 배경이 사라졌다
- 동영상 자동 재생이 막히면 얼어붙는 문제를 따로 처리했다
- 총량 상한·삭제 보호·용량 표시를 만들었다

**OBS 소스로 깔면 이 네 가지가 전부 없어집니다.** 기획서가 처음에 "OBS가 이미 잘 함" 이라고
쓴 판단이 옳았고, 사용자의 현재 직감도 그것과 같습니다.

## 9. 이 리포트가 다루지 않은 것

- **실제 예배에서의 조작 편의성** — 저는 브라우저로만 눌러 봤습니다. 실사용 피드백이

- **다른 봉사자의 학습 곡선** — OBS 를 알아야 한다는 것이 실제로 얼마나 부담인지는
  사용자가 판단할 문제입니다. 만약 이 부담이 크다면 D-A 의 답이 달라질 수 있습니다
- 비용·일정 추정 — '작다/중간/크다' 로만 적었습니다
