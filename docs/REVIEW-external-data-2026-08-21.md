1. **성경**: 제시된 `Beblia/Holy-Bible-XML-Format` 은 **쓰면 안 됩니다.** 라이선스가 없는데

3. **가장 확실한 이득**: OpenLyrics 가져오기/내보내기. 데이터 라이선스와 무관하고

## 2. 성경 — `Beblia/Holy-Bible-XML-Format` ⚖️ 쓰지 않기를 권합니다

### 확인한 사실

| 항목 | 값 | 확인 방법 |
|---|---|---|
| 라이선스 | **`null`** (없음) | GitHub API `license` 필드 |
| 크기 | **1.93 GB** | API `size` = 1,975,772 KB |
| 규모 | 200개 언어 · 1,000개+ 역본 · 트리 항목 1,051개 | API `git/trees` |
| README 문구 | "Use at your own discretion, no need to ask for permission, no warranty's" | README |

### 문제

저장소에 이런 파일들이 들어 있습니다.

```
EnglishNIVBible.xml      EnglishESVBible.xml     EnglishNASBBible.xml
EnglishCSBBible.xml      EnglishAmplifiedBible.xml
KoreanNKRVBible.xml      KoreanKLBBible.xml      KoreanWoorimalBible.xml
```

NIV(Biblica)·ESV(Crossway)·NASB(Lockman)·CSB(Holman)·개역개정(대한성서공회)은 모두
**현재 상업적으로 관리되는 역본**입니다. 저장소 소유자가 "허락 필요 없다"고 적어도,
그 사람은 이 역본들의 권리자가 아닙니다. **GitHub 에 올라와 있다는 사실이 권리를
정리해 주지 않습니다.**

우리 프로젝트는 지금 **방어할 수 있는 자리**에 있습니다 — 저작권 자료를 저장소에
넣지 않고, 사용자가 자기 자료를 갖고 있고, 앱은 그것을 읽을 뿐입니다. 이 저장소를
데이터 출처로 끌어오면 그 자리를 잃습니다. **얻는 것보다 잃는 것이 큽니다.**

### 그래도 남는 값어치: 포맷 참고 (데이터 아님)

파일 하나가 5 MB 남짓인 단순 XML 이라, **사용자가 합법적으로 가진** XML 을 읽는
어댑터를 만들 때 구조 참고는 됩니다. 다만 아래 `open-bibles` 가 **OSIS/USFX/Zefania**
표준을 쓰므로, 표준을 지원하는 편이 낫습니다.

NIV·ESV 는 배포할 수 없지만, **WEB·BSB 는 배포할 수 있습니다.**

### 한국어 — `kor-korean.osis.xml` ⚖️ 두 가지 문제

**어느 역본인가**: 본문을 받아 대조한 결과 **개역한글(1961)** 입니다.

```
창 1:3  하나님이 가라사대 빛이 있으라 ! 하시매 빛이 있었고
창 1:2  … 하나님의 신(神)은 수면에 운행하시니라
```

'가라사대'·'신(神)'·'어두움' 이 개역한글의 표지입니다. 우리 `krv` 와 창세기 1:1–8 을
정규화 대조한 결과 **8/8 일치** — 같은 본문입니다.

**문제 ①: 권리 표기가 비어 있습니다.**

파일 헤더의 `<rights/>` 가 **빈 태그**입니다. "Public Domain" 은 저장소 관리자의
판단이고, 출처는 Unbound Bible(Biola 대학) 의 `korean_utf8.zip` 입니다.

⚖️ 대한성서공회는 개역한글에 대한 권리를 주장합니다. 한국 저작권법의 업무상 저작물
보호기간(공표 후 70년)을 적용하면 1961 + 70 = **2031년**입니다. 반면 Biola 는 20년 넘게
자유 배포해 왔고 교회는 미국에 있습니다. **이건 제가 결론 낼 수 있는 문제가 아닙니다.**

> **추가 (2026-09-14)** — 이 ⚖️ 는 풀렸습니다. **대한성서공회 저작권 FAQ 가
> 『성경전서 개역한글판』의 저작재산권 보호기간(50년) 경과를 직접 밝히고 있습니다** —
> 저작권료 없이 사용 가능하되 인격권(동일성유지·성명표시)은 준수. 권리자 본인의 공지라
> 위 추정보다 강한 근거입니다. 같은 날 `scrollmapper/bible_databases` 의
> **한국어 개역한글(`sources/ko/KorRV`, 선언 라이선스 `Public Domain`)** 도 확인했는데,
> 아래 open-bibles 판과 달리 **−477절 누락이 없습니다**(창 30:32–43 · 창 33:20 모두 있음).
> 실측과 판정은 [BLOG-SERIES-PLAN.md §4](BLOG-SERIES-PLAN.md) 에 있습니다.

**문제 ②: 본문이 빠져 있습니다. 이게 더 실질적입니다.**

| | 절 수 |
|---|---|
| 우리 `krv` | **31,102** |
| open-bibles 한국어 | **30,625** |
| 차이 | **−477절 · 24권에서 불일치** |

창세기만 보면 **창 30:32–43 열두 절이 통째로 없고**(그 파일의 창세기 30장은 31절에서
끝납니다), 창 33:20 도 없습니다. 절 번호 합치기 관행 차이가 아니라 **본문 누락**입니다.

```
창 30:32  오늘 내가 외삼촌의 양떼로 두루 다니며 …   ← 우리에는 있다
창 30:33  후일에 외삼촌께서 오셔서 …                ← open-bibles 에 없다
창 30:34  라반이 가로되 내가 네 말대로 하리라 하고    ← open-bibles 에 없다
```

**예배 중 창세기 30장을 읽다가 32절에서 화면이 멈춥니다.** 그대로 쓸 수 없습니다.
(이미 겪은 부류의 문제입니다 — [KNOWN-DATA-ISSUES §1](KNOWN-DATA-ISSUES.md) 의
KJV 158절 잘림과 같습니다.)

기타 잡티: `!` 가 붙은 절 1,566개(5.1%) · 한자 괄호 주석 76개(0.2%). 이건 우리
`bible-sources.ts` 의 정제 규칙으로 처리할 수 있는 수준입니다.

## 5. 제안 — 우선순위 순

### ① OpenLyrics 가져오기·내보내기 ★ 가장 확실

**왜 확실한가**: 데이터 라이선스와 **무관합니다.** 포맷만 구현하는 것이고, 상호운용이
그 포맷의 존재 이유입니다. 그리고 우리 저장 구조와 **1:1로 대응**합니다.

```xml
<!-- OpenLyrics -->
<verse name="v1" lang="ko"><lines>만복의 근원 하나님</lines></verse>
<verse name="v1" lang="en"><lines>Praise God from whom all blessings flow</lines></verse>
```

```
# 우리 lyrics-parser.ts
[1절]
만복의 근원 하나님
| en Praise God from whom all blessings flow
```

같은 절 이름을 언어별로 반복하는 구조 → **우리 `|en` 태그와 정확히 같은 모델**입니다.
`lib/lyrics-parser.ts` 의 `parseLyrics`/`formatLyrics` 위에 어댑터 한 겹이면 됩니다.

**얻는 것 세 가지**

| 얻는 것 | 왜 값어치가 있나 |
|---|---|
| **내보내기** | 저작권 있는 가사를 우리 SQLite 밖으로 **표준 형식 백업**. 앱을 안 쓰게 되어도 가사가 갇히지 않는다 |
| **가져오기** | 사용자가 합법적으로 가진 OpenLyrics 곡을 읽는다. 지금은 텍스트 붙여넣기뿐 |
| **이사** | OpenLP·ProPresenter·EasyWorship 와 오간다. 다른 교회에 넘길 때 실질적 |

**비용**: `lib/openlyrics.ts` (순수) + 테스트 + 찬양 탭 버튼. 기존 곡집 반입
(`songbook-import.ts`) 과 같은 자리에 붙습니다.

### ② 배포용 성경 DB — 로드맵의 미해결 항목을 여기서 푼다

지금은 앱을 다른 PC 로 옮기면 성경이 없습니다. 제안:

**빌드에 `--profile` 을 둡니다.**

| 프로필 | 담는 것 | 용도 |
|---|---|---|
| `full` (기본) | 지금처럼 사용자 원본 폴더에서 12역본 | 이 PC |
| `distributable` | **WEB · BSB · KJV · ASV** (전부 PD, open-bibles) | 다른 봉사자 PC · Electron 패키지 |

한국어는 담지 않습니다 — 개역한글은 §3 의 두 문제가 있고, 개역개정은 배포 불가입니다.
대신 앱이 **처음 켤 때 "성경 원본 폴더를 고르세요"** 로 안내해 사용자 자료를 반입하게
합니다(지금 동작을 안내로 승격). 영어는 배포판에 들어 있으니 **한/영 병기 중 영어 쪽은
설치 직후부터 동작**합니다.

**구현 비용이 낮습니다.** 어댑터 구조가 이미 있습니다.

```ts
// scripts/bible-sources.ts — 지금
schema: 'android' | 'flat' | 'json'
// 더할 것
schema: 'osis' | 'usfx' | 'zefania'
```

`source-reader.ts` 의 `readSource()` 가 이미 스키마로 분기합니다. 새찬송가 교독문에
`kyodoc-parser.ts` 를 더한 것과 **같은 패턴**입니다.

**그리고 검증기가 이미 있습니다.** `scripts/verify-bible-db.ts` 가 절 수·누락을 잡습니다 —
그것이 open-bibles 한국어의 477절 누락을 찾아낸 방식입니다. 새 출처를 붙일 때
**반드시 통과시켜야 하고**, 통과하지 못하면 그 역본은 담지 않습니다.

⚠️ 한국어 개역한글을 배포판에 넣기로 한다면, 그 전에 **누락 477절을 우리 `krv` 로
메워야** 합니다. 그러면 '무엇이 원본인가' 가 흐려지므로, 저는 **넣지 않는 쪽**을 권합니다.

### ③ 성능 — 배포판은 저절로 작아집니다

지금 `bible.sqlite` **105 MB** 입니다. 12역본을 한 파일에 담기 때문입니다.

| | 예상 |
|---|---|
| `full` (12역본) | 105 MB |
| `distributable` (영어 PD 4역본) | **대략 25~35 MB** |

Electron 패키지에 넣기 훨씬 편해집니다. **다만 이건 추정입니다** — 실제로 빌드해
재야 합니다. 이 저장소의 규칙대로 **측정 전에는 수치를 문서에 박지 않습니다.**

역본별 파일 분리(`ATTACH`)는 지금 필요하지 않다고 봅니다. 105 MB SQLite 는 로컬
조회에서 문제가 되지 않고, 쪼개면 다역본 조인이 복잡해집니다. **문제로 확인된 뒤에**
손대는 편이 낫습니다.

못 쓰지만, **형식**은 참고할 수 있습니다.

우리 강사 모니터는 이미 **강사와 찬양팀**이 봅니다([USER-GUIDE §6.1](USER-GUIDE.md)).
찬양팀에게 가사만 보이고 코드가 안 보입니다. OpenLyrics 에도 인라인 코드가 있습니다
(`<chord name="B"/>`).

**제안**: ①(OpenLyrics)을 하면 코드 정보가 **덤으로 들어옵니다.** 그것을 강사 모니터에만
표시하고 회중 화면에는 내보내지 않습니다. 별도 데이터 수집이 필요 없습니다.

⚠️ 다만 이건 **사용자에게 물어야 할 기능**입니다 — 찬양팀이 실제로 원하는지 모르는 채
만들면 안 씁니다.

---

### ⑤ AGPL 주의 — `yozachar/hymnal`

제시된 저장소 중 **유일하게 라이선스가 있고**, 그것이 **AGPL-3.0** 입니다.

AGPL 은 네트워크로 서비스하면 소스 공개 의무가 생깁니다. 우리 앱은 로컬 서버지만
**태블릿에서 접속**하게 되어 있어, 그 코드를 가져다 쓰면 해석 여지가 생깁니다.

**권고**: 이 저장소의 **코드는 쓰지 않습니다.** 다국어 찬송가 UI 구조를 *읽고 배우는*
것은 문제없지만, 코드를 옮기면 우리 프로젝트 전체가 AGPL 이 될 수 있습니다.
