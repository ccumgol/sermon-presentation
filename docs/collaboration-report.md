## 0. 이 문서 사용 규칙 (중요)

작업을 시작·완료할 때 **이 문서를 먼저 읽고, 끝나면 갱신**해 주세요. 목적은 **중복 작업과
충돌 방지**입니다.

1. **착수 전**: 4장(작업 보드)에서 그 항목이 `🔴 미착수` 인지 확인하고, `🟡 진행중`으로 바꾸고
   본인 이름(Agent 명)과 날짜를 적습니다.
2. **완료 후**: `🟢 완료`로 바꾸고 **검증 방법과 결과**를 3장에 한 줄 남깁니다.
   (주장만 쓰지 말고 "무엇으로 확인했는지" 적어주세요)
3. **파일 충돌 주의**: 5장 "파일별 점유 현황"에서 다른 Agent가 만지는 파일과 겹치면
   먼저 6장 "인계 메모"에 남기고 조율합니다.
4. **커밋 정책**: Agent 가 작업 완료 후 **직접 커밋·푸시합니다.**
   - **브랜치는 `main` 직통**입니다(2026-08-14 사용자 결정). 예배 직전 급한 수정에
     병합 단계가 끼면 느려지기 때문입니다. 대신 **작게 자주** 커밋해 충돌 범위를 줄입니다.
   - 논리적 단위로 나눠 커밋하고(성격이 섞이면 분리), 메시지에 **원인·조치·검증**을 담습니다.
   - ⚠️ **푸시 전 점검 필수**: `git diff --name-only origin/main..HEAD` 로
     `data/`·`.claude/settings.local.json` 이 포함되지 않았는지 확인.
   - 협업 중이므로 푸시 실패 시 `git pull --rebase` 후 재시도합니다.
   - **이력 재작성(force push, filter-repo)은 사용자 승인 필요** — 다른 Agent 작업을 깨뜨릴 수 있음.
5. **착수할 때 "복구 정보"를 먼저 쓴다** (⚠️ 가장 중요 — 아래 0.1 참고).
   사용량 만료·크래시는 예고 없이 오므로, **끝난 뒤 쓰는 기록은 남지 않습니다.**
6. **사용자 데이터를 되돌리기 전에 반드시 묻는다** (⚠️ 이 프로젝트 고유 — 아래 0.2 참고).

## 0.1 중단(사용량 만료·크래시·강제 종료) 대응 규칙 ★필수

Agent 작업은 **토큰/사용량 소진, 세션 만료, 크래시**로 언제든 중간에 끊길 수 있습니다.
그 경우 "완료 후 갱신" 규칙만 있으면 보드에 `🟡 진행중` 만 남아, 다른 Agent 가
**"누가 하는 중이니 손대지 말자"** 고 오해해 작업이 정지합니다.

### 규칙 A — 착수 즉시 3줄을 먼저 기록 (선행 기록)
작업을 시작하면 **코드를 만지기 전에** 8장(진행 중 작업 로그)에 다음을 씁니다.
```
- [시작 2026-08-15 14:30 / Agent B] 찬미예수 2000 곡집 가져오기
  계획: scripts/import-songbook-folder.ts 신규 / 폴더 규약(번호 제목.txt) 파서 재사용
  다음 단계: 파서 단위테스트 → 미리보기 실행 → 사용자 확인 → --apply
```
중단돼도 **이 기록이 남아** 다음 Agent 가 이어받을 수 있습니다.

### 규칙 B — 긴 작업은 단계마다 한 줄 갱신
30분 이상 걸릴 작업은 단계가 끝날 때마다 `다음 단계:` 줄만 고칩니다.
(마지막으로 갱신된 지점이 곧 **중단 지점**입니다)

### 규칙 C — 이어받는 Agent 의 판정 절차
`🟡 진행중` 인데 담당자가 응답 없거나 오래됐다고 판단되면 **아래 근거로 직접 확인**하세요.
추측하지 말고 실제 상태를 보고 판단합니다.

```bash
# 1) 미커밋 변경 = 진행 중이던 흔적 (무엇을 만지고 있었는지)
git status --short
git diff                     # 어디까지 고쳤는지

# 2) 파일 수정 시각 = 마지막 활동 시점 (중단 시각 추정)
ls -lt lib/*.ts server/**/*.ts src/control/**/*.tsx scripts/*.ts docs/*.md | head

# 3) 남은 잔여물 확인
git stash list               # 중단 전 stash 했을 수 있음
git branch --no-merged main  # 미병합 작업 브랜치

# 4) 코드가 실제로 동작하는 상태인지 (반쯤 고친 상태일 수 있음)
npx tsc --noEmit
npx vitest run
```

**판정 기준 (제안)**
| 상황 | 판정 | 조치 |
|---|---|---|
| 미커밋 변경 있음 + 파일 수정이 **수 시간 이상 전** | 중단됨 | 8장 로그를 읽고 이어받기. 상태를 `🟡 진행중(인계: 본인)` 으로 갱신 |
| 미커밋 변경 없음 + 보드만 `🟡` | **착수 직후 중단** | 그 항목은 사실상 미착수 → `🔴` 로 되돌리고 새로 시작 |
| 테스트/타입검사 실패 | **반쯤 고친 상태** | 먼저 그 부분을 완성하거나 되돌린 뒤 진행 (사용자에게 보고) |
| 판단이 애매함 | — | **사용자에게 확인** (임의로 되돌리지 말 것) |

### 규칙 D — 되돌리기는 사용자 승인 후
중단된 작업의 미커밋 변경을 **버리는 것(`git checkout --`, `git stash drop`)은 사용자 승인
없이 하지 않습니다.** 다른 Agent 의 미완성 작업일 수 있고, 커밋 전이라 복구가 불가능합니다.

### 규칙 E — 사용자가 할 수 있는 최소 조치
Agent 가 갑자기 멈췄을 때 사용자는 다음 한 줄만 남겨도 충분합니다.
```
- [중단 2026-08-15 15:10] Agent B 사용량 만료로 중단. 위 항목 이어받을 Agent 필요.
```

## 0.2 사용자 데이터 취급 규칙 ★이 프로젝트 고유·필수

**이 프로젝트에서 가장 위험한 실수는 코드 버그가 아니라 사용자 데이터를 지우는 것입니다.**
실제로 한 번 일어났습니다(3.2 사고 기록).

이 프로젝트의 데이터(`data/songs.sqlite`)에는 **사용자가 UI 로 직접 손본 가사**가 들어 있고,
**git 에 들어가지 않으므로 되돌릴 방법이 백업뿐**입니다.

### 지켜야 할 것

1. **사용자는 Agent 가 작업하는 동안에도 병행해서 데이터를 편집합니다.**
   백업과 DB 가 다르다고 해서 "내 테스트 흔적"이라고 단정하지 마세요.
2. **되돌리기 전에 반드시 묻습니다.** 데이터를 원상복구하는 작업은 사용자 승인 후에만.
3. **파괴적 스크립트 실행 전 백업**:
   ```bash
   cp data/songs.sqlite "data/backups/songs-before-$(date +%Y%m%d-%H%M%S).sqlite"
   ```
4. **`lines_source = 'manual'`(승인) 은 사람의 작업 표시입니다.**
   자동 스크립트뿐 아니라 **Agent 도** 이 곡을 건드리지 않습니다.
   찬양 탭 목록에 초록색 `승인` 표로 보입니다.
5. **자기가 만든 변경만 목록으로 관리**하고, 정리할 때 그 목록에 있는 것만 되돌립니다.
6. **원본 성경 DB(`~/Desktop/Data/BibleDB`)와 찬양 자료 폴더(`~/Desktop/Data/Praise`)는
   읽기 전용으로만 엽니다.** 절대 쓰지 않습니다.

### 스크립트는 미리보기가 기본
데이터를 바꾸는 스크립트는 모두 **미리보기가 기본이고 `--apply` 를 붙여야 실제로 씁니다.**
새 스크립트를 만들 때도 같은 규칙을 따르세요.

```bash
npm run lyrics:realign          # 미리보기 (아무것도 쓰지 않음)
npm run lyrics:realign -- --apply
```

## 0.3 실행 환경 전제 — 같은 PC 공유 ★필수

**모든 Agent 는 사용자의 같은 맥에서 같은 `data/` 를 씁니다** (2026-08-14 사용자 결정).
데이터를 git 이나 별도 저장소로 공유하지 않습니다 — 찬양 가사는 사용자 개인 자료이고,
성경 DB 는 원본에서 다시 빌드할 수 있기 때문입니다.

그래서 다음 세 가지가 **동시에 일어날 수 있습니다.** 각각 대비가 필요합니다.

### (1) 사용자와 Agent 가 같은 DB 를 동시에 편집
`data/songs.sqlite` 는 WAL 모드라 동시 읽기·쓰기 자체는 안전하지만, **논리적 충돌**은
막아 주지 않습니다. 사용자가 검토 화면에서 가사를 고치는 중에 Agent 가 일괄 스크립트를
돌리면 서로의 결과를 덮어씁니다.

- 데이터를 바꾸는 스크립트를 **`--apply` 로 돌리기 전에 사용자에게 알립니다.**
- 실행 직전 백업은 예외 없이 남깁니다(0.2 참고).
- `lines_source='manual'` 인 곡은 어떤 경우에도 건드리지 않습니다.

### (2) 포트 7777 을 여러 Agent 가 잡으려 함
서버가 이미 떠 있으면 다음 포트를 자동으로 잡지만, **옛 프로세스가 구버전 코드로 응답**해
"수정이 반영되지 않은 것처럼" 보입니다. 실제로 여러 번 겪었습니다.

```bash
lsof -ti:7777 | xargs kill -9    # 내 서버를 띄우기 전에 확인
```

⚠️ 사용자가 예배 준비 중 띄워 둔 서버일 수 있습니다. **죽이기 전에 물어보세요.**

### (3) 미커밋 변경이 섞임
`main` 직통이므로 다른 Agent 의 미완성 변경이 작업 트리에 남아 있을 수 있습니다.
착수 전 `git status --short` 로 확인하고, 내 것이 아닌 변경이 있으면 8장 로그를 읽고
0.1 규칙 C 로 판정합니다. **임의로 되돌리지 않습니다.**

### 이 프로젝트를 처음 만지는 Agent 가 먼저 알아야 할 것

```bash
npm install
npm run bible:build     # 원본 성경 DB → data/bible.sqlite (읽기 전용으로만 원본을 연다)
```

  반영됩니다(브라우저 새로고침만으로는 안 됨 — 실제로 여러 번 헷갈렸음).
- 컨트롤 패널(React)은 `npx vite build` 로 `public/app/` 에 빌드합니다.

### 3.2 ⚠️ 사고 기록: 사용자가 직접 수정한 가사를 되돌림 (2026-08-14, 복구됨)

  3. 파괴적 작업 전 **백업**한다

### 3.4 헬라어 자간 벌어짐 — 폰트 체인 (2026-08-14)

- **데이터는 정상**이었음. 원인은 폰트 체인이 총칭 `serif` 로만 끝나, 총칭 폰트가
  다음절 그리스어(U+1F00 대역)를 못 덮어 **글자마다 다른 폰트로 대체**된 것.
- 판별법: **다음절 폭 ÷ 단음절 폭 비율**. 1.02 면 자체 글리프, 1.10 이면 대체.
- 총칭 앞에 Times New Roman 을 넣어 819.6px → 526.6px, 비율 1.02 로 정상화.
- **프리셋만 고쳐서는 부족했음** — 저장된 사본은 JSON 으로 굳어 있어, 초기화 때
  **옛 문자열과 정확히 같을 때만** 새 체인으로 올리는 마이그레이션을 넣음.

### 3.40 인용구가 저장에서 사라진 버그 · 프로젝터 글자 통일 (2026-08-20, Agent C)

**사용자 지적 두 가지**: ① '템플릿 업데이트' 를 누르면 인용구가 모두 성경 항목으로
바뀐다 ② 프로젝터의 순서 표시 글자를 첫 글자 크기로 고르게.

#### ① 화이트리스트에 새 필드를 더하지 않았다

`normalizeItems`(저장 경로)는 **아는 필드만 하나씩 옮겨 담는** 화이트리스트다.
모르는 쓰레기가 순서표에 박히지 않게 하는 옳은 설계지만, **새 필드를 넣을 때 그곳을
같이 고치지 않으면 그 필드가 저장할 때 조용히 사라진다.**

§3.38 에서 `quote`·`preview` 를 만들고 그곳을 고치지 않았다. 화면에서는 잘 보였으므로
**저장하기 전까지 알 수 없었다.** 사용자가 실제 사용 흐름("매주 미리 준비한 후에
'템플릿 업데이트' 로 저장을 대신해서 쓸 것 같다")을 말해 준 덕에 무엇이 문제인지가
분명했다.

교훈: 이 저장소는 **저장 경로가 화이트리스트**다. 항목에 새 필드를 더하는 작업은
`shared/types.ts` 만으로 끝나지 않는다. 그것을 잊지 않게 **왕복 테스트**를 만들었다 —
`tests/integration/plan-item-roundtrip.test.ts` 가 종류마다 **모든 선택 필드를 채운
항목**을 저장 경로에 통과시켜 하나도 빠지지 않았는지 본다. 새 필드를 넣고 그곳을
잊으면 실패한다.

그 테스트를 쓰면서 나머지 다섯 종류를 전부 대조했다 — **빠진 것은 없었다**
(`readingBook`·`songLabel`·순서 표시 필드 모두 잘 들어 있었다). 내가 가장 최근에
넣은 두 필드만 빠져 있었다.

테스트를 쓰다 내 fixture 가 세 번 틀렸다(`ItemBackground` 는 `src`/`source` 구조,
전례문 id 는 `lords-prayer`, 판본은 `traditional`). 셋 다 **정규화가 제대로 걸러 낸
것**이라 코드가 아니라 fixture 를 고쳤다.

#### ② 진짜 원인은 자동 리듬이 아니라 **수동 조정**이었다

'전체' 프리셋에 리듬 설정이 없어 프로젝터의 `--title-rhythm` 은 **이미 0** 이었다
(`clampRhythm(undefined) === 0`). 그런데 사용자 순서표의 `찬양과경배` 에 글자별 크기가
`0.8`·`0.9` 로 박혀 있었고, 그것은 **항목**에 담겨 렌더러가 **인라인**으로 꽂는다.
템플릿으로는 막을 수 없다.

먼저 데이터를 확인한 것이 진단을 갈랐다 — 템플릿만 보고 '이미 0인데?' 로 끝냈으면
사용자가 보고 있는 화면을 설명할 수 없었다.

CSS 로 덮었다. 인라인을 이기려면 `!important` 뿐이고, **렌더러가 만든 표시용 인라인을
표시 전용 화면에서 되돌리는** 이 자리가 그것이 옳은 경우다. 이 저장소에서 색·크기는
`body` 선언으로 처리했으므로(§3.36) 이것만 예외이고, 그 이유를 주석에 적었다.

자동 리듬도 `projectorTemplate()` 에서 **명시적으로** 0 으로 뒀다 — 지금은 없어도
같지만, 나중에 그 템플릿에 리듬을 넣어도 프로젝터는 고르게 남는다. 테스트로 고정했다.

#### OBS 는 건드리지 않았다

프로젝터만 고르게 한다. 실측으로 대조했다 — OBS 미리보기는 `120 · 115.2 · 96 · 108 ·
108px` 로 리듬이 살아 있다.

#### 확인한 것

| 확인 | 결과 |
|---|---|
| 인용구 넣고 '템플릿 업데이트' | 두 줄 모두 그대로 |
| DB | `quote: true` · `preview` · `paging` 살아 있음 · 일반 성경 항목과 구분 |
| 프로젝터 | 인라인 `0.8em`·`0.9em` 인데 **실제 다섯 글자 모두 96px** · 이동 `none` |
| OBS | 리듬 그대로 |
| 테스트 | 909개 통과 (14개 추가) |

**새 파일**: `tests/integration/plan-item-roundtrip.test.ts`

### 3.39 인용구 — 네 화면이 같은 글을 보이게 했다 (2026-08-20, Agent C)

**사용자 지적**: 인용구를 실행하면 관리자·OBS·강사 모니터·프로젝터의 말씀 형식이
모두 다르다. 네 가지를 나란히 적어 보내 주셨다.

#### 이 지적이 드러낸 구조적 문제

§3.38 에서 인용구를 만들 때 나는 **한 화면(관리자 목록)만 보고 끝냈다.** 같은 슬라이드가
네 렌더러를 지나는데 각자 참조·절 번호 규칙이 다르다는 것을 확인하지 않았다.

| 화면 | 규칙 |
|---|---|
| 관리자 목록 | `describeItem` 이 참조 + 미리보기 |
| OBS | 참조를 별도 줄로, 절 번호 붙임 |
| 강사 모니터 | 절 번호를 **늘** 붙임(설정을 보지 않음), 참조를 아래에 |
| 프로젝터 | '전체' 템플릿이 참조·절 번호 **둘 다 끔** |

교훈: **여러 화면이 같은 데이터를 다르게 그리는 구조라면, 새 기능은 네 곳에서 다 봐야
한다.** 프로젝터를 만들 때(§3.36) 이미 '렌더러가 넷' 이라는 것을 알고 있었는데도
§3.38 에서 그 목록을 다시 꺼내 보지 않았다.

#### 설정이 아니라 **글자**로 푼 이유

`showReference: 'inline'` 이라는 값이 타입에 있었지만 구현이 없었다. 그것을 구현하는
길과 참조를 본문 글자에 넣는 길을 놓고 사용자에게 선택지를 보여 드렸다.

글자로 넣는 쪽을 권한 근거: 참조가 별개 요소인 한 렌더러 셋을 각각 고쳐야 하고,
프로젝터는 템플릿이 참조를 끄므로 예외가 또 필요하다. **규칙이 넷이면 넷은 다시
어긋난다.** 글자로 넣으면 네 화면이 '본문' 으로 받으므로 어긋날 자리가 구조적으로
사라진다. 사용자가 그 길을 골랐다.

접두사는 **항목의 `ref`** 를 썼다 — 서버의 `slide.reference` 는 정식 이름
(`고린도전서 1:3`)이라 목록 줄과 달라진다. `ref` 를 쓰면 관리자 목록과 **글자까지**
같아진다.

#### 원본을 고친 것이 아니다

DB 는 손대지 않는다. 화면에 보낼 **사본**을 만든다(`quoteSlides` 는 불변이고 테스트로
고정했다). 이 저장소의 '원본 텍스트를 고치지 않는다' 원칙과 어긋나지 않는 자리다.

#### 사용자가 확인을 요구한 지점

"'성경'에서 본문을 호출했을 때는 달라지는 게 없는거지?" — 정확한 질문이었다.
`resolveItem` 이 `item.quote` 일 때만 변환을 부르므로 코드 경로가 갈린다. 말로만
답하지 않고 **실측으로 대조**했다: `창 1:1-6` 은 절 번호 `1`, 참조 줄 `창 1:1-6`,
보조 역본까지 예전 그대로다.

#### 의존성 0 검사가 제 일을 했다

`stage.js` 주석에 "…이라 import 할 수 없다" 라고 썼더니 **의존성 0 검사가 걸렸다**
(`/import\s|require\(/`). 검사가 주석의 낱말까지 본다는 것을 확인하고 문구를 바꿨다.
거칠지만 정확한 방향의 검사다 — 느슨하게 고치지 않았다.

#### 확인한 것 (네 화면 동시)

| 화면 | 나온 글 |
|---|---|
| 관리자 목록 | `고전 1:3 하나님 우리 아버지와 주 예수 그리스도로부터 은혜와 평강이 있기를 원하노라` |
| OBS(미리보기) | 같음 · 참조 줄 없음 · 절 번호 없음 |
| 강사 모니터 | 같음 (한 줄) |
| 프로젝터 | 같음 · 참조 줄 없음 · 절 번호 없음 |
| 성경 낭독 대조 | `1태초에…` + `1In the beginning…` · 참조 줄 `창 1:1-6` — **그대로** |
| 테스트 | 895개 통과 (18개 추가) |

**새 파일**: `tests/unit/quote-consistency.test.ts` (렌더러 두 곳의 규칙을 파일을 읽어 묶는다)

### 3.38 인용구 — 겹친 기능을 '성경 절 낱개'로 바꿨다 (2026-08-20, Agent C)

**요청**: 광고와 인용구가 겹친다. 인용구는 성경 본문을 **카테고리가 아닌 개별 슬라이드로**
가져오는 기능으로. `창 1:1-6` 을 넣으면 **타이틀 없이** 창 1:1 … 창 1:6 이 나온다.

상세 사용법은 [USER-GUIDE §1.4.05](USER-GUIDE.md).

#### 겹친다는 진단이 맞았다

광고와 인용구는 화면에서 **똑같이 그려졌다** — 둘 다 `kind: 'text'` 로 `renderText` 를
탄다. 실제 차이는 아이콘(💬/📝)과 `↩ 직전으로` 뿐이었다.

#### 사용자 데이터가 요청을 확인해 줬다

저장된 인용구 항목이 하나 있었고, 그 내용이 **`창 3:15`** 였다. 이미 참조를 인용구로
쓰려 했고, 지금은 글자 그대로 `창 3:15` 가 화면에 나갔다. 애매할 수 있는 요청을
데이터가 못 박아 줬다 — **먼저 데이터를 본 것이 설계 질문을 줄였다.**

#### 성경 항목과 같은 구조로 담은 것이 핵심 판단

`type: 'bible'` + `quote: true` 다. 자유 글자로 담으면 역본을 바꿀 수 없고 본문이
순서표에 복사된다. 같은 구조로 두면 역본·참조 표기·절 번호·글꼴·템플릿이 **공짜로**
쓰이고 **본문은 언제나 DB 가 원본**이다. 새 필드 둘은 모두 옵션이라 옛 순서표는
손대지 않는다.

`quote` 가 하는 일은 넷뿐이다 — 💬 아이콘 · `↩ 직전으로` · **제목 슬라이드 없음** ·
**펼치기 없음**. 뒤의 둘이 '타이틀 없이 바로' 를 만든다.

#### 실측이 설계를 고친 곳

처음에는 `itemTitle` 만 비웠다. 그런데 인용구를 클릭해도 **화면이 그대로**였다 —
성경 항목이라 여전히 '펼칠 수 있는' 것으로 취급돼, 클릭이 펼치기만 하고 제목이
없으니 아무것도 나가지 않았다. 절 하나 = 화면 하나이므로 **펼칠 것이 없다.**
`isExpandable` 에서 빼자 그 줄이 곧 슬라이드가 되어 **한 번 클릭으로 송출**됐다.
광고·순서 표시와 같은 취급이고, 설교 중 인용에 맞는 동작이다.

#### 목록 줄의 본문은 '라벨' 이라고 못 박았다

`창 1:1 태초에 하나님이 천지를 창조하시니라` 로 보여 달라는 요청이었는데, 컨트롤
패널은 **펼친 항목 하나만** 본문을 조회한다(`resolveItem`). 낱개 여섯 줄의 본문을
조회 없이 그릴 방법이 없어 `preview` 를 항목에 담았다(`songTitle` 과 같은 이유).

담는 순간 '두 개의 진실' 이 생기므로 **어느 쪽이 원본인지 문서와 주석에 못 박았다** —
화면에 나가는 본문은 언제나 DB 다. 그래서 preview 는 잘라도 되고(44자) 없어도 된다.
역본을 바꾸면 지우고 새 역본으로 다시 읽는다. 다시 읽기가 실패하면 **비워 둔다** —
틀린 글자를 보여 주는 것보다 참조만 보이는 편이 낫다.

#### 비동기 뒤의 덮어쓰기를 두 곳에서 막았다

역본을 바꾼 직후 미리보기를 다시 읽는 경로가 **옛 `items` 배열로 덮어써 역본 변경을
되돌렸다.** 코드를 쓰는 중에 발견해 `patchItems` 가 함수형 갱신을 받게 하고 그 경로를
함수형으로 바꿨다. 항목을 여러 개 넣는 `insertItems` 도 같게 했다 — 자리는 어긋나도
되지만 **항목이 사라지면 안 된다.**

`insertItem` 을 여섯 번 부르면 `items` 가 이 렌더의 값이라 마지막 하나만 남는다.
그래서 한 번의 patchItems 로 넣는 `insertItems` 를 따로 뒀다.

#### 옛 항목을 망가뜨리지 않았다

옛 자유 글자 인용구는 **그대로 나간다**(광고처럼 글자가 뜬다). 새로 만들 수만 없다.
사용자의 한 건은 요청에 따라 지웠고, 그 일을 스크립트로 만들었다
(`scripts/remove-text-quotes.ts` — 미리보기 기본 · **무엇을 지울지 내용까지 보여 준다**
· `--apply` 가 스냅샷을 먼저 뜬다). 순서표에서 사라진 한 줄은 예배 중에야 눈에 띈다.

### 3.37 프로젝터 — '기능은 있는데 찾을 수 없다' 를 고쳤다 (2026-08-20, Agent C)

**사용자 재요청**: 스크린샷으로 제목줄·출처줄을 빨간 박스로 표시하며 "없앨 수 없나".

#### 내가 첫 판에서 잘못 판단한 것

전체 화면(`F`)을 구현하고, 답변에서 "주소줄은 지울 수 없고 F 가 유일한 방법"이라고
**설명하는 것으로 일을 끝냈다.** 설명은 맞았지만 사용자는 도달하지 못했다.

원인을 둘로 본다 — `F` 를 눌러야 하는 것을 몰랐거나, **키보드 초점이 브라우저 쪽에
있어서** `F` 가 페이지에 닿지 않았다(창을 열고 바로 누르면 실제로 그렇게 된다).

교훈: **제약을 설명하는 것과 제약 안에서 도달 가능하게 만드는 것은 다른 일이다.**
브라우저 규칙은 못 바꾸지만, 그 규칙이 요구하는 '사용자 동작' 을 **가장 찾기 쉬운
동작(클릭)** 으로 만들 수는 있었다. 처음부터 그렇게 했어야 했다.

#### 한계선을 지킨 곳

브라우저는 사용자 동작 없이 전체 화면에 들어가지 못한다. 우회할 방법이 없고, 찾으려
해서도 안 된다(피싱 방지 장치다). 그래서 **자동으로 켜지 않고, 사용자의 첫 동작에
얹었다** — 클릭이나 키 입력에만 얹는다. 마우스 이동에는 얹지 않았다: 브라우저가 그것을
사용자 동작으로 인정하지 않아 거절되고, **거절되면 다시 시도할 기회를 잃는다.**

#### 클릭으로 나가지는 않게 했다

들어가는 것만 클릭에 얹었다. 나가는 것까지 얹으면 예배 중 실수로 벽에 브라우저 창이
드러난다. 막대를 누른 클릭도 제외했다 — `+` 를 누르려다 전체 화면이 되면 안 된다.

#### 안내는 상시 띄우지 않았다

프로젝터는 같은 자리가 오래 비치면 번인 위험이 있다. 안내는 **전체 화면이 아닐 때만**
막대와 함께 나오고 함께 숨는다. 전체 화면이 되면 할 말이 없으므로 사라진다.

#### 아이콘을 코드로 그렸다

'앱으로 설치' 를 크롬이 제안하려면 192·512 PNG 가 필요하다. 그림 파일을 넣는 대신
`scripts/make-projector-icons.ts` 가 `node:zlib` 만으로 그린다 — 이미지 도구를 깔지 않아도
되고, **무엇을 그렸는지 읽어서 알 수 있다**(바이너리는 diff 가 되지 않는다).
PNG 는 서명+IHDR+IDAT+IEND 네 덩이면 되고, CRC32 표만 직접 만들면 된다.

#### 확인하지 못한 것을 확인하지 못했다고 적었다

**전체 화면이 실제로 켜지는 것은 이 환경에서 볼 수 없었다.** 검증에 쓰는 임베드 브라우저
창이 Fullscreen API 자체를 막는다(`TypeError: Permissions check failed`). 합성 클릭도,
CDP 로 보낸 실제 클릭도 통과하지 못했다.

그래서 `requestFullscreen` 을 스파이로 감싸고 **실제 클릭·실제 `F` 가 호출까지 가는지**
확인했다(둘 다 호출됨, 기억 저장됨, 거절돼도 화면 정상 · `diag.errors = 0`).
브라우저가 허용하는지는 표준 동작에 맡겼다 — 사용자 환경에서 안 되면 이 기록이 출발점이다.

**새 파일**: `scripts/make-projector-icons.ts` · `public/projector/manifest.webmanifest` ·
`public/projector/icon-{192,512}.png`

### 3.36 프로젝터 화면 — OBS 와 동시에 다른 배치 (2026-08-20, Agent C)

**요청**: TV 가 아니라 프로젝터로 띄우면 선명하지 않아 글자를 크고 두껍게 해야 한다.
강사 모니터처럼 별도 창, '전체 — 성경·찬송 겸용' 처럼 표시, 주소줄·시계·제목·다음
화면·연결됨·글자 크기 라벨 전부 삭제, 풀스크린, 마우스 올릴 때만 막대(+/− 글자 크기),
색 반전 옵션.

상세 설계는 [plan-projector.md](plan-projector.md).

#### 렌더러를 복제하지 않은 것이 이 작업의 중심 판단

`output.js` 는 1044줄이고 성경·찬양·교독문·전례문 렌더러가 다 들어 있다. 새 페이지를
만들면서 이것을 복제하는 것이 가장 쉬운 길이었지만, 두 곳이 갈라지면 **한쪽만 고친
것을 예배 중에 알게 된다.** 그래서 프로젝터 페이지는 같은 DOM id 를 두고 같은 CSS·같은
스크립트를 불러오고, `projector.css`/`projector.js` 가 덧칠만 한다.

의존성 0 이라 import 할 수 없으므로 이 규칙은 **파일을 읽는 테스트**로 지킨다
(`tests/unit/projector-page.test.ts` 10개). 이 저장소에 이미 있는 방식이다.

#### 서버와 화면이 싸우지 않게 만든 방법

서버의 `style:patch` 는 CSS 변수를 `<html>` **인라인**에 꽂는다. 인라인을 이기려면
`!important` 나 자바스크립트로 인라인을 지우는 수밖에 없어 보였는데, 둘 다 서버와
화면이 같은 값을 두고 싸우는 구조가 된다.

**CSS 변수는 상속으로 결정된다** — 값을 읽는 `.line-primary` 에서 가장 가까운 조상의
선언이 이긴다. `body` 는 `html` 보다 가까우므로 `body.projector { --primary-color: … }`
한 줄로 끝났다. 서버는 제 일을, 화면은 제 일을 한다.

#### 내가 8/19 에 오진한 것을 이번엔 설계로 막았다

autoFit(넘칠 때 줄여 주는 기능)은 `+` 버튼과 싸운다 — 키우면 넘치고, 넘치니 되돌려
깎아서 **글자 크기가 안 바뀌는 것처럼 보인다.** 8/19 에 이 현상을 autoFit 탓이라고
했다가 실제로는 브라우저 창이 720p 였던 일이 있다. 이번엔 프로젝터에서만 autoFit 을
끄고(`autoFitMinScale: 1`), 대신 **넘치는 동안 막대에 알린다** — 잘린 글을 조작자가
눈치채지 못하면 회중이 못 읽는다. 두 원인을 TROUBLESHOOTING §3.4 에 나란히 적었다.

#### 실측이 설계를 바꾼 곳

처음 띄워 보니 교독문 **회중 줄이 42px** 였다. '전체' 템플릿의 둘째 줄 값인데, 그것은
OBS 에서 *둘째 역본*을 곁들일 때를 생각한 크기다. 프로젝터에서 둘째 줄은 곁가지가
아니다 — **한/영 병기 찬양의 영어 가사**(이 교회는 미국 한인교회다)이고 **교독문의
회중 줄**이다. 대비가 낮은 벽에 42px 로 비치면 회중이 읽을 수 없다.

`max()` 로 **바닥만 받쳤다**(첫 줄의 0.72배 이상). 템플릿이 이미 큰 값을 주면 그것을
쓴다 — 덮지 않고 아래로만 막는다. 교독문 회중 줄만은 첫 줄과 같은 크기로 뒀다.
교독문 전용 템플릿이 그렇게 만들어져 있다("색으로만 구분한다").

#### 요청 중 하나는 할 수 없다고 말했다

**주소줄은 웹페이지가 지울 수 없다.** 있다면 피싱 페이지가 은행 주소를 위조할 수 있어
모든 브라우저가 막아 둔 것이다. 전체 화면이 유일한 길이고, 그러면 주소줄뿐 아니라
탭·창 테두리까지 사라진다 — 요청 두 개("주소줄 없애기", "풀스크린")가 한 동작으로
모인다. 브라우저 규칙상 사람이 누르는 순간에만 되므로 창을 열면 6초간 안내를 띄운다.

### 3.35 교독문 두 벌 — 통일찬송가용 / 새찬송가용 (2026-08-20, Agent C)

**요청**: 지금 들어 있는 교독문은 통일찬송가의 것이다. 새찬송가 교독문 DB
(`~/Desktop/Data/Kyodoc.sqlite`)로 새로 넣고, 고를 때 두 벌을 구분하게 해 달라.

#### 덮어쓰지 않고 **나란히** 둔 이유

`number` → **`(book, number)`** 로 바꾸고 기존 76편을 `hymn_old` 로 옮겼다. 곡집과 같은
이름(`hymn_old`/`hymn_new`)을 쓴 것은 이미 그 말을 쓰는 곳이 있기 때문이다.

#### 없으면 통일찬송가용으로 본다

`reading` CueItem 의 `readingBook` 은 **없어도 된다.** 없으면 `hymn_old` 다. 새찬송가용을

저장한 데이터를 건드리지 않고 기능을 늘리는 방법이라, 마이그레이션이 실패할 여지가 없다.

#### 원본을 고치지 않았다

원본 5번 '시편 8편'이 내용을 두 번 반복하고 `(다같이)` 줄이 중간(13/24)에 있다.
뒤 절반은 앞과 조금 다르다(오타로 보이는 '이니이다'). **고치지 않고 알렸다** —

못박는다.

'하단' 의 값은 **사용자가 실제 화면을 보며 조정한 것**이다(옛 `id 3`). **코드에** 넣었다 —
DB 덮어쓰기로 두면 '원본 불러오기' 가 옛 프리셋 기본값으로 가 버려 뜻이 반대가 된다.

#### 프리셋 덮어쓰기 — `getTemplate` 의 순서를 뒤집었다

전에는 프리셋이 코드 상수라 서버가 수정을 거부했고(409), 템플릿 탭이 저장할 때 **강제로
복제**해 사용자 사본이 넷 쌓였다. `getTemplate` 을 **DB 먼저 → 코드 대체**로 바꾸니
다섯 버튼이 자연스럽게 나왔다 — 덮어쓰기는 행 쓰기, **원본 불러오기는 행 지우기**다.
**코드가 곧 원본**이라 백업이 날아가도 프리셋은 되살아난다.

지우기와 되돌리기는 **다른 동사**로 뒀다. 프리셋에 `DELETE` 는 여전히 409 —
코드에 있는 것을 '지운다' 는 말이 성립하지 않고, 두 뜻을 한 동사에 담으면 잘못 눌렀을 때
무엇이 일어날지 알 수 없다.

#### 나눈 기준 두 가지

- **모양은 템플릿, 켜고 끄기는 항목** — 참조 표기·소제목·절 번호. 크기·색은 매주 같지만
  '이 본문에는 소제목을 띄우자' 는 그 주에 정하는 일이다. 값은 **세 갈래**
  (`템플릿 따름`·`켬`·`끔`) — 체크박스면 '템플릿을 따른다' 와 '일부러 껐다' 를 구분할 수 없다
- **글꼴은 항목, 나머지 모양은 템플릿** — 성경·찬양도 고딕/명조를 항목에서 고른다.

**표시 여부 결정은 출력 페이지에서 한다.** 컨트롤이 미리 풀어 담으면 나중에 템플릿만

### 3.31 찬양 표시 언어 · 영어 가사 붙여 넣기 (2026-08-18, Agent C)

`ca650b4` `434d9c3`

**한/영 병기는 구조가 이미 완성돼 있었다.** `song_lines(section_id, line_index, lang, text)`
에 `UNIQUE(section_id, line_index, lang)` — 성경의 `(translation_id, book, chapter, verse)`
와 같은 발상이다. 격리 환경에서 확인했더니 네 가지 언어 조합이 모두 다른 덱을 냈고

그 데이터를 넣는 일을 손으로 하면 4절 × 4줄 = 16번을 정확히 맞춰야 하고, 한 줄만 밀려도
어느 번역이 어느 줄에 붙는지 어긋난 채 저장된다. 그래서 **번역만 순서대로 붙여 넣게

그 기본값을 바꿀 길조차 없었다 — 결과적으로 순서표의 찬양은 **영구히 한국어만** 나갔다.

문서에 정정을 남겼다.

붙이기 도구는 **한국어를 한 글자도 고치지 않는다** — 읽기만 하고 그대로 다시 쓴다.

> **저작권이 갈리는 지점**: 통일 40장 「주 하나님 지으신 모든 세계」 = How Great Thou Art

### 3.30 교독문·전례문 표시 옵션 + 살아 있는 화면 반영 (2026-08-18, Agent C)

`4f2d318` `2f9840a`

사용자 아이디어 셋 중 둘의 구현. 강사 모니터 글자 크기(60~260%, `+`/`-`/`0` 키,
localStorage 기억)와 전례문 폰트(고딕/명조)·글자 크기다.

**핵심은 절대 행간**이다. `line-height: calc(1em + Npx)` — `1em` 은 글자 크기를 따라가고
`+Npx` 는 고정이라, 글자를 키워도 줄 간격이 함께 부풀지 않고 겹치지도 않는다.
상대 배수(`1.4`)면 키울 때 간격이 벌어지고, 순수 px 면 키울 때 겹친다.
교독문 16px · 전례문 10px (1920×1080 실측).

**그다음 사용자가 보고한 버그**: 폰트나 크기를 바꿔도 **청중용 화면이 그대로**였다.
출력 쪽은 정상이었다 — WS 로 `style` 을 직접 보내니 64→102.4px, 명조 적용, 행간 고정
유지가 모두 확인됐다. 컨트롤도 `style: {font, scale}` 을 제대로 실어 보냈다.
빠진 것은 **다시 보내기**였다: 항목을 고쳐도 이미 나가 있는 슬라이드를 다시 만들지 않아
`▶` 를 새로 눌러야 반영됐다. 폰트·크기는 '돌려 보면서 맞추는' 값이라 눈이 따라오지
않으면 옵션이 없는 것과 같다.

이 관용구(`liveItemId === id` 면 다시 송출)는 **담당자 크기·글자 조정에 이미 있었는데**
교독문·전례문 칸에만 빠져 있었다. `patchReading`·`patchLiturgy` 에 채웠으므로 판본·배경·
화면 넘김·본문 고치기도 함께 따라온다. 보고 있던 장에 머물도록 `currentIndex` 를 넘기고,
슬라이더를 끌 때 늦게 온 옛 응답이 새 화면을 덮지 않도록 120ms 모아 보낸다
(교독문은 본문을 서버에서 다시 읽어 온다).

순서표 **전체**가 올라간 경우는 일부러 그대로 둔다 — 덱을 다시 만들면 예배 중 진행
위치를 잃는다. 대신 왜 안 바뀌는지와 무엇을 눌러야 하는지를 항목 칸에 적었다.
`▶` 로는 안 된다는 것도 실측으로 확인해 문구에 담았다(`goto` 는 올라간 덱 안에서
자리만 옮긴다).

> **내가 낸 회귀를 발견해 고쳤다**: `110eac5` 의 '한 줄 합치기' 에서
> **'예배용으로 올리기' 버튼이 합쳐진 게 아니라 지워져 있었다.** 순서표 전체를 올릴 길이
> 없어 화살표로 끝까지 진행할 수 없었다. `.plan-actions > button.primary` 의 `flex: 2` 가
> 원래 이 자리를 위한 CSS 였다.

> **측정 함정**: 처음에 "자동 축소가 크기 증가를 되돌린다" 고 진단했는데 **틀렸다.**
> 출력 무대는 창 크기를 따라가므로 720p 창에서는 `--fit-scale` 이 최소값 0.6 까지
> 내려가 증가를 상쇄한다. **1920×1080 에서는 `fit 1.00`** 으로 그대로 적용된다.
> 실측은 반드시 1080p 에서.

### 3.29 강사 모니터 `/stage` — 2개 모니터 (2026-08-18, Agent C)

D-A 결정("OBS 유지 + 강사 모니터만 자체 창")의 구현. 요청했던 **2개 모니터 별도 출력**이다.

| 화면 | 어디로 | 무엇 |
|---|---|---|
| 강단(회중) | **OBS 브라우저 소스** (`/output/?layer=main`) | 본문·가사. 카메라·배경과 합성 |
| 강사 | **우리가 띄우는 창** (`/stage/`) | 지금 화면 · 다음 화면 · 진행 · 시각 |

**강사 화면은 OBS 를 거치지 않는다.** 회중에게 나가는 화면이 아니라 조작자용 정보이므로
투명 배경도 알파 합성도 필요 없다. 브라우저 창 하나를 강단 모니터에 전체화면으로 두면
끝이다 (ProPresenter 의 Stage Display, EasyWorship 의 Foldback 과 같은 방식).

**검수 리포트에서 예상한 것보다 서버 변경이 작았다.** '상태를 layer 별로 나눠 보낸다'
까지 갈 필요가 없었다 — 강사 화면은 **같은 상태를 다르게 그리는** 것이다. 실제로 필요한
서버 변경은 둘뿐이었다:

1. **덱을 강사 모니터에도 보낸다** (`wantsDeck`). 전에는 컨트롤 패널 전용이었는데,
   '다음 화면' 이 강사 모니터의 존재 이유라 지금 슬라이드만으로는 부족하다.
   OBS 출력에는 여전히 보내지 않는다 — 쓰지 않는 데이터를 예배 중 계속 밀어 넣을 이유가 없다
2. **OBS 출력 수와 따로 센다** (`connections.stage`). 섞으면 'OBS 연결됨' 표시가
   거짓이 된다 — 강사 모니터만 붙어 있는데 OBS 가 붙은 것처럼 보인다

**출력 페이지와 같은 원칙: 의존성 0.** 예배 중 이 화면이 죽으면 설교자가 다음을 모른다.
연결이 끊겨도 **마지막 화면을 그대로 둔다** (테스트가 `onclose` 에서 화면을 지우지 않는지
검사한다). 오래된 상태 메시지를 버리는 규칙(`knownRevision`)도 같다.

**시각을 넣은 이유**: 경과 시간이 아니라 **현재 시각**이다. 설교자가 아는 것은
'몇 시에 끝내야 한다' 이기 때문이다.

**작업 중 고친 것**: 항목 하나만 단독으로 올리면 `groups` 가 없어 그룹 이름이 '—' 로
비었다. 덱 이름으로 대신한다 — 강사가 지금 무엇을 하는 중인지 알 수 없으면 안 된다.

**검증**: 통합 10개 추가, 694 passed. 격리 서버에서 교독문 7장을 올려 강사 화면에
'지금 2/7 · 다음 · 이후 3·4·5·6' 이 따라오는 것, **블랙을 켰을 때 강사 화면에
경고가 뜨는 것**, 컨트롤 패널의 'OBS 미연결' 이 강사 모니터 접속에 흔들리지 않는 것을
확인(스크린샷).

> 남은 것: 강사용 **설교 노트**. 지금은 순서표에 노트 필드(`note`)가 있지만 강사 화면에
> 보여 주지 않는다. 실제로 쓰게 되면 그때 붙이는 것이 맞다.

### 3.28 D-B 덜어내기 — 배경·미디어를 OBS 에 넘김 (2026-08-18, Agent C)

기획서 §1.3 이 처음부터 「영상/이미지 배경 재생」을 **범위에서 제외**했다
("OBS가 이미 잘 함"). 중간에 만들었다가 검수 뒤 원래 판단으로 되돌렸다.

**먼저 사용자 데이터를 확인했다** — 쓰는 것을 지우면 안 된다:

| | 결과 |
|---|---|
| 템플릿 4개의 배경 모드 | 전부 `transparent` |
| 순서표 6개의 `media` 항목 | **0개** |
| 항목 배경 | 0개 |
| `data/backgrounds/` 올린 파일 | **0개** |

아무것도 쓰고 있지 않아 **데이터 이전 없이** 덜어냈다.

**덜어낸 것** — 1,227줄 삭제 / 206줄 추가 = **순 1,021줄 감소**

| 무엇 | 왜 |
|---|---|
| 업로드 API (`POST`) · 64MB 한도 · base64 본문 | 파일은 폴더에 직접 넣으면 된다 |
| 삭제 API (`DELETE`) · 템플릿 사용 중 409 보호 | 업로드가 없으니 삭제도 앱의 일이 아니다 |
| 총량 상한(2GB) · `totalBackgroundBytes` · 507 | **보안 위험 S-1 이 여기서 나왔다 — 함께 사라졌다** |
| `media` CueItem (예배 전 안내 그림·동영상) | OBS 씬 하나로 훨씬 잘 된다 |
| `video` 배경 모드 · `tryPlay`(자동 재생 재시도) | OBS 미디어 소스는 자동 재생·코덱 문제가 없다 |
| `holdMsFor` (항목별 머무는 시간) | `media` 전용이었다 |

**남긴 것**: 교독문·주기도문·사도신경의 **항목별 배경**(`ItemBackground`). 이건 OBS 로
대체하기 어렵다 — 순서 항목마다 배경이 바뀌어야 하는데 OBS 로 하면 씬을 항목 수만큼
만들어야 한다. **고르기만** 남기고 올리기·지우기는 없앴다.

동영상은 목록에서도 뺐다 — 고를 수 있게 두면 다시 브라우저에서 재생하게 된다.

**검증**: 684 passed (덜어낸 기능의 테스트 316줄도 함께 정리). 격리 서버에서
업로드 `POST` 404 · 삭제 `DELETE` 404 · `media` 항목은 '알 수 없는 종류' 로 거부 ·
**교독문 배경은 출력 화면까지 그대로** 확인(스크린샷).

### 3.24 새 항목이 고른 항목 다음에 들어가게 (2026-08-18, Agent C)

사용자 신고: "특정 순서를 클릭한 상태에서 새 항목을 만들면 경우에 따라 맨 하단에 생겨서
순서 조정이 힘들다."

**원인**: `insertItem` 이 `cursor + 1` 을 항목 번호로 썼는데 **`cursor` 는 화면 줄 번호**다.
펼친 항목의 슬라이드가 줄로 끼어들어 둘이 어긋난다.

```
줄0  📖 요 3:16      ← 항목0 (펼침)
줄1    슬라이드 1
줄2    슬라이드 2
줄3  🎵 찬송가       ← 항목1
```

줄3 에서 넣으면 `cursor + 1 = 4` 인데 항목은 2개뿐이라 `slice` 가 맨 끝을 가리켜 **끝에
붙었다.** '경우에 따라' 였던 이유가 이것이다 — 펼친 항목이 없으면 줄 번호와 항목 번호가
같아서 제대로 동작했다. 슬라이드를 보며 작업할 때(=펼친 상태)만 틀렸다.

**고침**: 규칙을 순수 함수 `insertIndexFor(rows, cursor, itemCount)` 로 빼고, 줄이 가리키는
`itemIndex + 1` 을 쓴다. 넣은 뒤 커서도 **줄 번호**로 옮긴다 (항목 번호를 그대로 넣으면
같은 이유로 어긋난다).

**검증**: 단위 6개 추가(펼친 항목 뒤·슬라이드 줄·접힌 목록·구분 줄·빈 목록·범위 밖),
677 passed. 격리 서버에서 주기도문을 펼쳐 **슬라이드 3번 줄**을 고른 채 넣으니 주기도문
바로 다음에 들어갔고, 구분 줄·항목 줄에서도 각각 그 다음에 들어가는 것을 확인.

폴더가 없는 PC 에서도 기동되게 **있을 때만** 붙인다.

**배경을 템플릿이 아니라 항목에 뒀다.** 템플릿에 두면 배경을 바꿀 때마다 템플릿을 새로
만들어야 한다. 이 순서들은 글 스타일은 그대로 두고 배경만 바꾸므로 항목 쪽이 맞다.
새 타입 `ItemBackground = { src, source: 'library'|'data', fit? }`.

**'무조건' 을 어떻게 지켰나**: 예배 기본 설정에 「교독문·전례문 배경」 하나를 두고, 앞으로
넣는 교독문·주기도문·사도신경 항목이 그것을 자동으로 받는다. 항목마다 고르게 하면
잊어버린 한 장이 맨 화면으로 나간다. 항목별 변경도 된다.

**주소는 정해진 표로만 만든다.** 순서표에 담긴 값이 주소를 통째로 정하게 하면 WS 로 아무
주소나 밀어넣어 바깥 그림을 불러오게 할 수 있다. 폴더 이름은 두 개뿐이고
(`BACKDROP_PREFIX`), 파일 이름 검증은 배경 업로드와 **같은 함수**를 쓴다.

**작업 중 찾아 고친 것 — 배경을 정하는 곳이 세 군데였다**

출력 페이지를 새로 열면 배경이 빠졌다. **OBS 브라우저 소스를 새로고침하면 그대로 겪는
문제**라 그냥 둘 수 없었다. 브라우저에서 호출 스택을 찍어 보니 배경을 그리는 곳이 셋이었다:

1. `render` — 슬라이드가 바뀔 때
2. `applyTemplate` — 템플릿 메시지가 올 때
3. **`applyStylePatch` → `applyBackdropFromString`** — 템플릿 CSS 패치의 `backdrop` 키

접속 직후 서버가 상태와 템플릿을 잇달아 보내는데, 3번이 뒤에 와서 항목 배경을 지웠다.
결정하는 곳이 여럿이면 도착 순서에 따라 결과가 달라진다.

`syncBackdrop(payload)` 하나로 모았다 — **안내(media) → 항목 배경 → 템플릿 배경** 순.
템플릿이 원하는 값은 `templateBackdrop` 에 기억만 하고 그리지 않는다.
`applyBackdrop` 직접 호출은 세 갈래(안내·템플릿·항목)만 남았고, **테스트가 그 개수를
고정한다** — 늘어나면 결정 지점이 또 흩어졌다는 뜻이다.

부수 수정: 기본 설정 칸을 열 때 배경 목록을 읽지 않아 드롭다운이 비어 '배경이 없다'로
보였다.

| 줄 구성 | 짝수 41편(순수 교대) · 홀수 35편(교대 + 마지막 `(다같이)`). **예외 없음** |
| 보이지 않는 문자 | U+200B 78개(구분 줄), U+2024 1개(`3․1절` 의 점) |
| 줄 길이 | 중앙 30자 · 최대 87자 — 66%가 24자를 넘는다 (교독문은 절 하나가 한 줄) |

**본문을 한 글자도 손대지 않는다.** 절기 교독문은 줄마다 성구 표기가 붙고(`(행 1:8)` —
줄마다 다른 책에서 온다), 시편 교독문은 마지막에 절 범위(`(1-6)`)가 붙는다. 둘 다 주보에
그렇게 인쇄되므로 떼지 않는다. `(다같이)` 표시도 회중에게 필요한 정보다. 무엇을 뗄지
판단하기 시작하면 76편마다 예외를 다루게 되고, 그 판단이 틀리면 예배 중에 드러난다.

**짝 묶기는 저장하지 않는다.** 줄을 그대로 담고 화면 단위는 `readingSlides` 가 계산한다.
저장 데이터에 화면 구성을 박아 두면 나중에 바꿀 수 없다. 홀수면 마지막 `(다같이)` 줄이
**혼자 한 화면**을 쓴다 — 앞 화면에 세 줄로 붙이지 않는다(성격이 다른 줄이다).

**출력은 템플릿의 주/보조 텍스트 역할로 그린다.** 인도자 = 주, 회중 = 보조. 성경 다역본과
같은 장치라 어느 템플릿에서도 이미 스타일이 잡혀 있고, 누가 읽을 차례인지 눈에 보인다.

**작업 중 고친 것 둘**

1. 목록 검색에서 `23` 을 치면 본문에 '23' 이 든 편까지 **7건**이 나왔다. 숫자만 쳤으면
   본문은 보지 않고 번호·제목만 본다 (`시편 23편` 도 찾아야 하므로 제목은 본다).
   번호가 정확히 맞는 편을 맨 위로 올린다
2. 후보 40개가 패널을 넘쳐 아래 내용과 겹쳤다. `.add-bar .candidates` 를 스크롤 상자로
   바꿨다 — 잘라서 감추면 없는 것처럼 보인다

**검증**: 단위 14 + 통합 12 추가, 659 passed. 실제 파일로 가져오기 미리보기 →
76편·879줄·457화면, 문제 0건. 격리 서버에서 검색(`23`/`시편 98`/`성탄절`/`즐거이`) ·
23번 추가 → 7화면 분할 → **출력 화면에 인도자 줄(크게)·회중 줄(작게)·`시편 98편` 표기**
확인. 사용자 자료 폴더와 `data/` 는 건드리지 않았다.

> 목록 응답은 본문 줄을 싣지 않는다 — 76편 × 12줄이면 70KB 가 넘고, 고르는 데는
> 번호·제목·화면 수만 필요하다. 실측 6,664바이트.

### 3.21 전례문을 교회 본문으로 교체 (2026-08-17, Agent C)

사용자가 출석 교회에서 쓰는 주기도문·사도신경 네 본문을 직접 주었다.
판본 이름도 바뀌었다 — **'새번역/전통(개역한글)' → '개역개정/개역한글'**.

키(`new`/`traditional`)는 **그대로 뒀다.** 이미 저장된 순서표가 그 값을 담고 있어서,
키를 바꾸면 지난 순서표의 판본 지정이 깨진다. 이름만 바꿔도 화면에 보이는 것은 다 바뀐다.

**낱말은 그대로, 끊는 자리는 다시 잡았다.**

받은 본문의 줄바꿈에는 붙여 넣은 폭에서 생긴 자리가 섞여 있었다 — 개역한글 주기도문의
`뜻이 하늘에서 이룬 것 같이 땅에서도` / `이루어지이다`. 그대로 두면 화면에서 구가 끊긴다.
**찬양 가사에서 고쳤던 그 문제다.** 그래서 낱말은 한 자도 바꾸지 않고 끊는 자리만 의미
단위(24자 이내)로 다시 잡았다.

**낱말 대조로 확인했다** — 네 본문 모두 공백을 정규화한 낱말 나열이 원문과 완전히 일치.
자동 대조 스크립트를 돌려 한 낱말이라도 다르면 어디인지 찍히게 했다.

교회 표기 그대로 남긴 것 (다른 판본과 헷갈리는 자리라 테스트로 고정했다):

| 판본 | 표기 |
|---|---|
| 주기도문 개역한글 | `나라이 임하옵시며` · `우리의 죄를` · `대개 나라와 권세와 영광이` |
| 사도신경 개역개정 | `거기로부터 살아 있는 자와 죽은 자를` · `거룩한 공교회와 성도의 교제와` |
| 사도신경 개역한글 | `저리로서 산자와 죽은 자를` · `거룩한 공회와` |

**아멘 처리가 바뀌었다.** 교회 본문은 `…아버지의 것입니다. 아멘.` 처럼 마지막 구와 아멘이
한 줄이다. 아멘만 떼면 고아 줄이 되므로 붙여 뒀고, 테스트도 '아멘으로만 된 줄' 에서
'끝이 아멘' 으로 바꿨다.

**사용자에게 물어볼 것 세 가지** — 붙여 준 그대로 옮겼으나 화면에 나가면 눈에 띈다:
`빠지지않게`(띄어쓰기), `장사한지 사흘만에`(띄어쓰기), `'본디오 빌라도'`(따옴표).
원문을 임의로 고치지 않는 것이 규칙이라 그대로 뒀다.

**검증**: 단위 19개(교회 표기 고정 포함), 633 passed. 격리 서버(7812)에서 토글이
`개역개정 ★ / 개역한글` 로 뜨고 본문이 실제로 바뀌는 것, `땅에서도 이루어지이다,` 가 한 구로
붙어 나오는 것, 출력 화면 렌더까지 확인.

### 3.20 예배 전 안내 — 그림·동영상 항목 (2026-08-16, Agent C)

'예배 순서' 탭 요청 **5번**(마지막). 자동 진행은 이미 있었다 — `divider.auto`

설교 본문 뒤에 그대로 남는다.

**작업 중 고친 것**: 자동 진행 타이머의 의존성에 `deck?.slides`(배열)를 넣어, 상태가 올

### 3.18 예배 유형 관리 — 이름 바꾸기·복제·삭제 (2026-08-16, Agent C)

'예배 순서' 탭 요청 **2번(템플릿 업데이트·순서 저장/불러오기)** 과 **3번(광고 Enter)**.

**먼저 확인한 것**: 둘 다 이미 있었다. 유형 넷(주일예배·수요예배·새벽기도회·부흥회),
템플릿 업데이트, 순서 저장하기/불러오기, 광고 Enter(Enter=추가, Shift+Enter=줄바꿈).
없는 것만 채웠다 — 되는 것을 다시 만들지 않았다.

**빠져 있던 것**: 유형을 **만들고 갱신할 수만** 있었다. 저장된 순서는 불러오기 목록에서
✕ 로 지울 수 있는데 유형은 그 길이 없었다. 그래서
'주일예배' → '주일 1부 예배' 로 고칠 수도, 안 쓰는 '부흥회' 를 치울 수도 없었다.
서버에는 `PUT`(부분 수정)·`/duplicate`·`DELETE` 가 이미 다 있었고 **UI 만 없었다.**

| 버튼 | 무엇 |
|---|---|
| ⧉ | 유형 복제 — '주일 1부' 를 놔둔 채 '2부' 를 만드는 길. 비슷한 유형을 여럿 두는 것이 실제 운영이다 |
| ✎ | 이름 바꾸기 — 이름만 보낸다. 지금 화면의 항목을 함께 보내면 저장 안 한 편집까지 조용히 굳는다 |
| ✕ | 유형 삭제 — 마지막 하나면 '모두 지우면 다음 시작 때 기본 유형이 되살아납니다' 를 미리 알린다 |

같은 이름으로 바꾸려 하면 막는다. **이름이 곧 '덮어쓰기' 의 기준**이라 같은 이름이 둘이면
어느 쪽을 덮어쓸지 알 수 없어진다.

**작업 중 고친 것**: 이름 바꾸기를 열면 커서가 이름 끝에 붙어, 새 이름을 치는 순간

### 3.17 주기도문·사도신경 항목 (2026-08-16, Agent C)

'예배 순서' 탭 요청 6가지 중 **1번(순서 표시 항목)**. 대표기도·설교 제목·축도 등은
이미 `text` + `variant: 'order'` 로 있었고 **제목만** 띄웠다. 주기도문·사도신경은
회중이 함께 읽으므로 **본문 전체**가 필요해 새 항목(`type: 'liturgy'`)으로 만들었다.

**본문을 순서표에 복사하지 않는다.** 항목에는 `textId` + `version` 만 담고 글은
`lib/liturgy-texts.ts` 에서 온다 (찬양이 `songId` 를 담는 것과 같다). 그래서
판본 바꾸기가 한 글자로 끝나고, 오탈자를 고치면 지난 순서표까지 함께 고쳐진다.

- 판본 토글 — 새번역(기본) / 전통(개역한글). **select 가 아니라 버튼 두 개**로 둔 것은,
  접어 두면 다른 판본이 있다는 것 자체를 모르고 지나치기 때문이다
- 화면 넘김 2·4(기본)·6줄·전체. 고아 줄 방지는 찬양의 `chunkWithoutOrphans` 를 그대로 쓴다
- **본문 고치기** — 교회마다 '나라이/나라가' 처럼 갈리는 자리가 있다. 고치면
  `overrideLines` 에 담기고 내장 본문을 이긴다(찬양의 '승인'과 같은 원칙).
  '직접 고침' 배지 + '내장 본문으로 되돌리기'

**작업 중 고친 것 두 가지**

1. 미리보기 effect 가 `expandedItem?.id` 만 봐서, 판본을 바꿔도 슬라이드 목록이
   그대로였다(토글이 먹통으로 보인다). 항목을 직렬화한 값으로 바꿨다 —
   성경 '화면 넘김'·찬양 언어를 바꿀 때도 같은 문제가 있었다
2. 본문 편집이 매 입력마다 빈 줄을 걸러내 **Enter 로 줄을 늘릴 수 없었다.**
   고치는 동안은 입력한 그대로 두고(`liturgyDraft`), 항목에는 걸러낸 결과를 반영한다

**검증**: 단위 18 + 통합 11. 격리 서버(7808, 임시 데이터 폴더)에서 추가 → 판본 토글 →

사용자 서버(7777)와 `data/` 는 건드리지 않았다.

### 3.15 H-3 WebSocket Origin 검사 (2026-08-16, Agent C)

브라우저의 CORS 는 WebSocket 에 적용되지 않는다. 오퍼레이터가 예배 중 아무 사이트나

### 3.9 순서 표시 배치 — '순서 이름 | 담당자 + 밑줄' (2026-08-15)

사용자가 실제 예배 화면 캡처를 보내 같은 형태를 요청했다.

- `SlidePayload` 에 **`kind: 'order'`**(title · presenter) 추가. `text` 로 두지 않은 이유는
  두 값의 **자리가 다르기 때문**이다 — 줄 배열로는 "이건 왼쪽, 저건 오른쪽"을 출력 페이지에
  알릴 방법이 없다.
- 나누는 규칙은 `lib/plan-deck.ts` 의 `splitOrderText` 순수 함수(테스트 5건).
  첫 줄=순서 이름, 나머지를 합친 것=담당자, 빈 줄은 버린다.
- **담당자가 없으면 밑줄도 없다.** 빈 밑줄만 떠 있으면 이름을 못 넣은 것처럼 보인다.
- `.order-row` 만 **안전 영역 전체 폭**을 쓴다. 템플릿 블록 폭이 `auto` 면 글자 길이만큼만
  넓어져 두 값이 딱 붙는다.
- 항목별로 `좌우`(기본) / `쌓기` 선택. **기본값은 저장하지 않는다** — 순서표에 기본값이
  박히면 나중에 기본을 바꿀 수 없다.

**검증**: 브라우저 1920×1080 실측 — 순서 이름 좌측 끝(x=60), 담당자 우측 끝(x=1860),
밑줄이 이름 왼쪽(x=1176)까지 이어짐. 담당자 없는 항목은 오른쪽 칸이 만들어지지 않음.
`npx vitest run` **493 passed**.

### 3.10 ⚠️ 사고 기록: 새 슬라이드 종류가 OBS 화면에 조용히 안 나옴 (2026-08-15)

**증상**: 순서 표시 배치를 `쌓기`(kind `text`)로 하면 나오는데 `좌우`(kind `order`)로 하면
아무 일도 일어나지 않았다.

**원인**: OBS 안의 출력 페이지가 **옛 판**이었다. 서버를 재시작해도 그 페이지는
WebSocket 만 자동 재연결하고 **JS 는 메모리에 있던 것 그대로**다. 권장 설정상
'장면 활성화 시 새로고침'도 꺼져 있어 저절로 갱신되지 않는다.
옛 판은 `RENDERERS['order']` 가 없어 렌더에 실패하는데, 출력 페이지는 **모르는 내용을
받으면 화면을 비우지 않고 이전 내용을 유지**하도록 되어 있다(예배 중 검은 화면 방지).
그래서 **검은 화면이 아니라 "안 바뀜"** 으로 나타나 원인을 찾기 어려웠다.

**조치**: 사람이 기억해야 하는 절차로 두지 않고 **앱이 알리게** 했다.
출력 페이지가 접속할 때 자기가 로드된 시각을 보내고, 서버가 `public/output/` 파일
수정 시각과 비교해 컨트롤 패널에 노란 배너를 띄운다(`server/output-build.ts`).
'모르면 경고하지 않는다'가 기본이다 — 예배 직전 헛경고가 더 나쁘다.

**교훈**: 출력 페이지의 **계약(슬라이드 종류)을 늘리는 변경은 배포 문제와 함께 온다.**
서버·컨트롤 패널은 재시작·새로고침으로 갱신되지만, OBS 안의 페이지는 **사람이 눌러야만**
갱신된다. 새 `kind` 를 더할 때는 옛 판이 그것을 받으면 어떻게 되는지 함께 생각한다.

### 3.11 ⚠️ 사고 기록: '공백' 항목이 아무 일도 하지 않음 (2026-08-15, 수정됨)

**증상**: 예배 순서의 '공백'을 송출해도 **이전 화면이 그대로** 떠 있었다.

**원인**: 공백 슬라이드가 내용을 지우지 않고 `body.blanked`(투명도 0)만 켰는데,
바로 뒤 `applyState` 가 `setBlank(live.blank)` 를 부르며 그 클래스를 **다시 껐다**.
`live.blank` 는 `B`(블랙)를 눌렀을 때만 참이므로 공백 항목은 **항상** 무효였다.

**진짜 원인은 개념이 겹친 것**이다.
- **블랙(B)** = 내용을 **남긴 채** 숨기기 (즉시 복구가 목적)
- **공백** = 내용이 **없는** 슬라이드

둘이 같은 장치(`blanked` 클래스)를 쓰면서, 하나가 다른 하나를 지웠다.

**조치**: 공백은 `clearSlide()` 로 내용을 실제로 지우고, `blanked` 는 `B` 전용으로 뒀다.
'내용 없음'(비우기) 경로도 같은 함수를 쓰게 해 두 곳이 어긋나지 않게 했다.

**교훈**: 화면을 비우는 방법이 둘 이상이면 **어느 쪽이 이기는지** 정해 둬야 한다.
출력 페이지는 상태를 눈으로 확인하기 어려워, 이런 겹침은 조용히 지나간다.

  **축소된 스크린샷으로는 구분이 안 돼**, 1:1 크기로 다시 찍고서야 알았다.
- 그래서 컨트롤 패널이 **실제 쓰이는 폰트**를 재서 보여 준다(작업 보드 4.2 항목 완료).

출발**한다(0 이나 1 에서 시작하면 조금만 건드려도 화면이 튄다).
단독 송출 중이면 움직이는 즉시 다시 보내 눈으로 보며 맞춘다.

⚠️ 실측으로 잡은 것 두 가지 — 외곽선 0 을 `none` 으로 적으면 **선언이 통째로 무시돼

둘 다 **랜을 열 때만** 의미가 있다. 지금은 `127.0.0.1` 고정(H-1)이라 같은 PC 에서만 닿는다.
"태블릿으로 조작할 계획이 있는가"를 확인했고, **당장은 없다**는 답을 받았다.

태블릿의 이점을 따져 보니 — 설교자가 강대상에서 직접 절을 넘기는 것 하나만 태블릿이어야
가능하고, 나머지(실제 투사면을 보며 조작)는 두 번째 모니터로 대체된다. 반면 비용은
**키보드 단축키 상실**(`PlanPanel`·`ReviewPanel` 의 `↓↑`/`j k`/`Enter`/`Tab` — 예배 중
안 보고 누르던 것을 화면을 봐야 누르게 된다), **예배 중 와이파이 끊김**, 교회 공용망 노출이다.

**되살리는 조건** — 셋 중 하나라도 생기면 5·6번을 먼저 하고 랜을 연다:
1. 설교자가 본인이 넘기고 싶어 하신다
2. 조작자가 두 명 이상이 된다
3. 조작석이 OBS PC 에서 물리적으로 떨어진다

그때 필요한 것은 **접속 암호 + 요청 수 제한 + 터치용 큰 버튼**, 반나절~하루. 미리 해두지
않는다 — 안 쓰는 기능에 붙은 암호는 잊어버리기만 한다. 참고로 컨트롤 패널은 900px 미만에서


  재시작**해야 반영됩니다. 옛 프로세스가 7777 을 잡고 있으면 구버전이 응답해

  옛 판이 떠 있으면 **새로 만든 슬라이드 종류가 화면에 나오지 않습니다** — 출력 페이지는
  모르는 내용을 받으면 이전 화면을 유지하므로(의도된 안전 동작) 검은 화면이 아니라

  ```bash
  for p in $(lsof -ti:7777); do ps -o pid,lstart,comm -p $p | tail -1; done
  ```
