## 1. KJV 원본에 앞부분이 잘린 절 158건 ⚠️ 복원 불가

`KJV.db` 자체에 절 앞부분이 없는 행이 158건 있다. 원본에서 동일하게 확인했다.

| 참조 | 원본에 저장된 내용 | 실제 KJV 본문 |
|------|-------------------|--------------|
| 시 23:1 | `of David. The LORD [is] my shepherd;…` | `A Psalm of David. The LORD [is] my shepherd;…` |
| 시 19:1 | `, A Psalm of David. The heavens declare…` | `To the chief Musician, A Psalm of David.…` |
| 시 120:1 | `of degrees. In my distress I cried…` | `A Song of degrees. In my distress…` |
| 민 14:25 | `and the Canaanites dwelt in the valley.…` | `(Now the Amalekites and the Canaanites dwelt…` |
| 신 1:2 | `days [journey] from Horeb…` | `Eleven days [journey] from Horeb…` |

시편 표제(superscription)와 괄호로 시작하는 절에 몰려 있다. 원본 DB를 만든 쪽에서
표제나 괄호 구간을 걷어내는 처리를 하다가 앞부분이 함께 날아간 것으로 보인다.

**영향**: KJV를 송출하면 해당 절이 문장 중간부터 시작한 것처럼 보인다.
**대응**: 데이터만으로는 복원할 수 없다. 검증기가 158건을 기준치로 추적하며,
이보다 늘어나면 실패로 처리한다. KJV를 주 역본으로 쓸 계획이면 다른 KJV 소스를
구해 교체하는 것이 근본 해결책이다.
**우회**: 한국어 흠정역(`kjvko`)에는 이 문제가 없다.

## 2. 히브리어 에스더 3:12 누락 → 교정함 ✅

`히브리어.db` 에 에스더 3:12가 아예 없고, 그 본문이 **8:9의 두 번째 행**으로
들어가 있었다. 원본 `bible` 테이블은 (책,장,절)에 유일성 제약이 없어 가능한 상태다.

확인 근거:
- 해당 행이 "첫째 달"(`בַּחֹדֶשׁ הָרִאשׁוֹן`)과 하만의 명령을 말한다 → 3:12의 내용
- 진짜 8:9는 "셋째 달 시완월 23일"과 모르드개의 명령을 말한다
- 개역개정 3:12("첫째 달 십삼일에 … 하만의 명령을 따라")와 일치

**대응**: `scripts/bible-sources.ts` 의 `DUPLICATE_FIXES` 에 근거를 적어 3:12로 옮긴다.
이동 대상 자리가 비어 있을 때에만 적용되므로, 원본이 나중에 고쳐지면 자동으로 비활성된다.

## 3. 역본별 장 구분 차이 3건 ✅ 정상

성경 판본에 따라 장을 나누는 방식이 다르다. 오류가 아니다.

| 역본 | 책 | 장 수 | 표준(개역개정) | 사유 |
|------|-----|------:|--------------:|------|
| 히브리어 원문 | 요엘 | 4 | 3 | 마소라 본문은 요엘을 4장으로 나눈다 |
| 공동번역 | 요엘 | 4 | 3 | 같음 |
| 공동번역 | 다니엘 | 14 | 12 | 13장(수산나)·14장(벨과 용) 추가부 포함 |

요엘의 절 수까지 대조해 확인했다: 개신교 2:28-32 = 마소라 3:1-5, 개신교 3장(21절) = 마소라 4장(21절).

**대응**: `lib/books.ts` 의 `CHAPTER_VARIANTS` 에 명시했다.
- `books.chapter_count` = 표준 장 수 (화면 표기·탐색용)
- `books.max_chapter_count` = 번들된 역본 중 최대 (참조 파싱 검증용)
- `translation_chapters` 테이블 = 역본별 실제 장 수

파서는 `욜 4:1`·`단 13:1` 을 받아들이고, 해당 장이 없는 역본은 조회 시
`PassageBlock.unavailable` 로 처리한다.

## 4. ESV — 파일이 두 개 있고 `ESV.db` 를 쓴다 ✅ 결론

원본 폴더에 ESV 파일이 두 개 있다. `14_ESV.db` 는 스키마와 마크업 면에서 깔끔해
보이지만, **31,086절 전수 비교 결과 본문이 손상된 파생본**이었다.

| | `ESV.db` ← **사용** | `14_ESV.db` |
|---|---|---|
| **`LORD` (YHWH) 보존** | ✅ **5,566절** | ❌ **0절** — 전부 `Lord` 로 |
| **`GOD` (YHWH) 보존** | ✅ **300절** | ❌ **0절** |
| **구두점 앞 공백 오류** | 0건 | ❌ **2,472절** (`the Lord ,`) |
| 스키마 | `bible(book, chapter, verse, content)` — 유일하게 다름 | android 스키마 |
| HTML 태그 | 3,100절 (`<block>`, `<span class="j">`) | 0 |
| HTML 엔티티 | 10,454절 (`&quot;` 등) | 0 |
| 빈 절 | 15개 (정상 — 아래 참고) | 애초에 없음 |
| 따옴표 | 곧은 `"` | 굽은 `" "` |
| 절 수 | 31,101 (정제 후 31,086) | 31,086 |

책별 절 수는 빈 절을 제외하면 **완전히 동일**하다. 본문 차이도 따옴표·대소문자·
공백을 정규화하면 사라진다. 즉 같은 판본에서 나온 두 파일인데, `14_ESV.db` 쪽이
**작은대문자 조판을 평문으로 풀면서 대소문자를 잃고 구두점 앞에 공백을 남겼다.**

영어 성경에서 `LORD`(대문자)는 신명사문자 **YHWH**를, `Lord`는 **Adonai**를 옮긴
것으로 구별이 의미를 갖는다. 실제 영향:

```
ESV.db    : The LORD is my shepherd; I shall not want.      (시 23:1)
14_ESV.db : The Lord is my shepherd; I shall not want.
14_ESV.db : Cain said to the Lord , "My punishment is …"    (창 4:13 — 쉼표 앞 공백)
```

**결론**: `ESV.db` 를 쓴다. flat 스키마와 HTML 마크업은 어댑터·정제로 이미 흡수했고
검증까지 끝났으므로 실질적 단점이 아니다.

**이 PC 에서는 `14_ESV.db` 를 휴지통으로 옮겼다** (2026-08-13). 열등한 중복본이라
혼동만 남기기 때문이다. 코드에는 **품질 저하 대체본** 설정을 남겨 두었다 —
원본 폴더 구성이 다른 다른 PC 에서 `ESV.db` 가 없을 경우 없는 것보다는 나으며,
사용 시 빌드가 경고를 띄우고 리포트 상단에 사유를 표시한다.

검증기가 `LORD` 표기 절 수와 구두점 앞 공백을 검사하므로, 잘못된 파일로 바뀌면
빌드가 아니라 **검증에서 걸린다**.

> `ESV.db` 의 이름을 바꾸거나 지우지 말 것. `bible-quote`·`bible-search` 스킬도
> 이 파일을 함께 읽는다(두 스키마를 런타임에 자동 감지한다). 열등한 파일로
> 이름만 바꿔치면 스킬도 조용히 `LORD` 를 잃는다.

### ESV 빈 절 15개는 정상

마 17:21, 마 18:11, 마 23:14, 막 7:16, 막 9:44 등 — **사본상 근거가 약해 ESV가
의도적으로 뺀 절**이다. 빈 절은 넣지 않으므로 절 번호에 구멍이 생긴다
(ESV 16개 장, 헬라어 1개 장, 히브리어 7개 장). 정상이며 검증기가 경고로만 알린다.

### ESV 소제목은 복원할 수 없다 ⚠️

`14_ESV.db` 에 `bible_theme` 2,429행이 들어 있지만 **어느 책·어느 장의
소제목인지 알 수 없다**:

- `bible.ThemeCd` 가 31,086행 전부 **0** → 본문과의 연결이 끊겨 있다
- `bible_theme.KindBCd` 가 2,429행 전부 **1** → 책 코드가 아니다
- `bible_theme` 에 장 컬럼이 없다 (`StartJul`/`EndJul` 만 있음)

남은 단서는 `ThemeCd` 순서(1..2429)와 절 범위뿐이다. 순서대로 성경을 훑으며
절 범위가 리셋되는 지점으로 책·장 경계를 추론할 수는 있지만, **한 곳만 틀려도

것은 소제목이 없는 것보다 나쁘므로 넣지 않는다.
(`ESV.db` 에는 `bible_theme` 테이블이 아예 없다.)

영어 소제목이 필요하면 **NIV(2,120건)** 를 쓰면 된다.

## 5. 한국어 전문검색은 FTS5로 부족하다 ⚠️ 설계 반영

FTS5 `unicode61` 토크나이저는 한국어를 **어절 단위**로만 쪼갠다.
'사랑'으로 검색하면 '사랑하사'·'사랑은'·'사랑하시는'이 걸리지 않는다.

측정 (개역개정, 311,223절 DB):

| 방식 | '사랑' 결과 | 소요 |
|------|-----------:|-----:|
| FTS5 `unicode61` | 26건 | 17.6ms |
| `LIKE '%사랑%'` | **557건** | 20.6ms |
| FTS5 `trigram` | 0건 | — |
| FTS5 `unicode61` (NIV 'love') | 526건 | 2.8ms |

`trigram` 토크나이저는 부분일치를 지원하지만 **3글자 미만 질의를 처리하지 못한다**.
'사랑'·'은혜'처럼 2음절 검색어가 한국어에서 가장 흔하므로 쓸 수 없다.

**대응 (검색 전략)**:
- 한국어 역본(`ko`) → `LIKE '%검색어%'` 부분일치. 역본 1개당 약 20ms, 11역본 전체 약 119ms
- 영어·헬라어·히브리어 → FTS5 어절 검색 (빠르고 랭킹 지원)

Phase 3 검색 UI 구현 시 역본 언어에 따라 전략을 갈라야 한다.
검증기가 `FTS < LIKE` 관계를 고정 검사하므로 이 전제가 깨지면 알 수 있다.

## 6. 히브리어·헬라어는 유니코드 정규화가 필요하다 ⚠️ 설계 반영

DB에 저장된 히브리어와, 소스 코드나 사용자 입력의 히브리어가 **결합 문자 순서가
달라** 눈으로는 같아도 `===` 비교가 실패한다.

```
stored : "בְּרֵאשִׁ֖ית"  (12자)
expect : "בְּרֵאשִׁ֖ית"  (12자)
===          → false
NFC 정규화 후 → true
```

**대응**: 히브리어·헬라어를 비교하거나 검색할 때는 양쪽 모두 `.normalize('NFC')` 를
거친다. 검증기의 스팟 체크가 이미 그렇게 한다. Phase 3 검색 입력에도 적용해야 한다.
